# M1-c3：扫描结果接入 net80211（实现说明）

> 目标：把 M1-c1/c2 已经拿到的 `scanBss[]` 变成 net80211 的 `ic_tree` 节点，
> 让系统 Wi-Fi 菜单 / `airport -s` 出现真实网络列表。
> 状态：**✅ 真机验证通过（2026-11-17 23:20，r4）**：菜单栏 Wi-Fi 列表出现邻居网络；
> 驱动侧 187 帧喂入 net80211、14 个 `ic_tree` 节点、11 次 `SCAN_DONE`。
> 过程中修复的 4 个前置缺陷与 3 个扫描链路缺陷见 [`docs/13`](13-M1-c3-卡死诊断与修复.md)。
> 最后更新：2026-11-17 23:25

## 一、结论先行

M1-c3 的本质只有一句话：**把固件上报的 beacon / probe response 原始帧，
在 workloop 上下文里喂给 `ieee80211_input()`**。

net80211 自己会完成建节点、填字段、发 WCL 事件这三件事，驱动不需要手工填
`ni_essid` / `ni_rates` / `ni_rsnie_tlv`（docs/09 里的路径 B 已被放弃）。

同时，本次在代码里定位到**三个必须一起修的前置缺陷**，只补喂帧是看不到结果的：

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `ieee80211_proto_attach()` 会把 `ic_newstate` 换成 net80211 自己的状态机，`attach()` 里早先装的 `ath_newstate` 被静默覆盖 | `ath_newstate` 从未被调用（`newstate=... (not implemented yet)` 这行日志一次都没出现过就是证据） | `ieee80211_ifattach()` 之后保存 `defaultNewState`，再重新装 `ath_newstate` |
| 2 | `enable()` 只置 `IFF_UP` | WCL 的 `beginWCLScan()` 第一道门是 `ic_if.if_flags & IFF_RUNNING`，不满足直接返回 `kIOReturnNotReady`，系统根本发不出扫描请求 | `enable()` 置 `IFF_UP｜IFF_RUNNING`；bring-up 成功后再补一次 |
| 3 | 从未发过 `IEEE80211_EVT_DRIVER_READY` | WCL 不会认定网卡可用，`DriverAvailable` 不上报 | bring-up 结束时发；若此时 handler 还没装（`AirportItlwm::start()` 晚于 bring-up），第一轮扫描结束时补发一次 |
| 4 | `publishHardwareProperties()` 只在 bring-up **开始**时调用 | ioreg 里永远是 `hardware-status = "not-started"` 和空值，所有阶段结果都看不到 | bring-up 结束时补一次；之后每轮扫描结束再刷新一次（顺带让 `ath10k-scan-ssids` 反映本轮） |

另外还有一条**语义前提**：`ic_opmode` 在 `bzero(&ic)` 后是 `0`，而本工程用的是
`IEEE80211_STA_ONLY` 构建（IBSS 枚举被编译掉），`0` 是非法值。现在在 `attach()`
里显式设为 `IEEE80211_M_STA`。

## 二、Sequoia 上真正生效的通路

docs/09 里记录的 `getSCAN_RESULT()` 遍历 `ic_tree` 属于**旧路径**（非 AIRPORT_WCL）。
本机型用的 `AirportItlwm-Sequoia` scheme 定义了 `AIRPORT_WCL` + `AIRPORT_IO80211_TARGET=15.2`，
扫描结果走的是：

```
WMI MGMT_RX（beacon / probe response）
  → [驱动] ieee80211_input()
  → [net80211] ieee80211_recv_probe_resp()
       · 建/更新 ic_tree 节点（ni_essid / ni_rates / ni_rsnie_tlv / ni_age_ts…）
       · #ifdef AIRPORT_WCL 时发 IEEE80211_EVT_BEACON
  → [WCL] AirportItlwmSkywalkInterface::handleWCLEvent(BEACON)
  → publishWCLBeacon(node, ies, len)
  → AirportWCL::ScanResult 消息 → 菜单栏 Wi-Fi 列表
```

扫描结束：

```
[驱动] ieee80211_end_scan(ifp)
  → IEEE80211_EVT_SCAN_DONE → WCL scanCompleted=true → scanSource->setTimeoutMS(0)
  → fakeScanDone() → completeWCLScan() → ScanDone 消息
```

所以 `ieee80211_end_scan()` 是**必须调用**的：WCL 只有收到 `SCAN_DONE` 才会结束
系统侧那一次扫描请求，否则要等它自己的 20 秒超时。

`end_scan()` 在找不到可连接 AP 时会走 `notfound → next_scan → newstate(SCAN)`，
这正好形成"未连接时持续扫描"的原生行为。我们把它记成 `scanWorkRerun`，
在本轮 worker 结束后再排下一轮，不会重入。

## 三、实现结构

### 3.1 线程模型（关键）

WCL 的 `BEACON` 回调会直接 `postMessage`，属于 **RX 上下文**（iwx 也是在 workloop
的 task 里调 `ieee80211_inputm`）。而一次全信道 WMI 扫描要轮询 10 秒以上，
绝不能放在 workloop 上。因此拆成两段：

```
thread_call（runScanWork）
  ├─ PDEV_SET_PARAM / SCAN_CHAN_LIST（必要时补）
  ├─ START_SCAN + 轮询收集事件（最长 12 s + 2 s 收尾）
  │    └─ MGMT_RX → applyScanInfo → stageScanFrame（只做定长拷贝）
  └─ runScanCompletion()
        └─ IOWorkLoop::runAction(scanCompletionAction)
              ├─ ieee80211_free_allnodes(ic, 0)      清上一轮节点
              ├─ 修正 ic_bss->ni_chan（next_scan 依赖它）
              ├─ feedStagedScanFrames()              mbuf + find_rxnode + ieee80211_input
              └─ ieee80211_end_scan(ifp)             发 SCAN_DONE
```

为什么扫描线程不直接喂帧：帧数据在 `wmiRxBuffer` 里，下一个 CE2 包就会覆盖；
而且从非 workloop 线程改 `ic_tree` / 触发 WCL 回调都没有保护。

暂存区容量：`16 帧 × 768 B`。超长（带大量 VHT/HE IE）或超量的帧被丢弃，
但会计入 `ath10k-scan-stage-overflow`，便于判读。

### 3.2 代码位置

| 文件 | 改动 |
| --- | --- |
| `hw/Ath10kWmiScan.hpp` | `WMIScanInfo` 增加 `mgmtFrame` / `mgmtFrameLength`（原始帧指针）；新增 `wmiFreqToChannel()`；新增 `kWmiScanMaxFrameBytes` |
| `Ath10kHal.hpp` | M1-c3 方法声明 + 状态字段（扫描轮数 / 喂帧计数 / 暂存区 / `defaultNewState` / `driverReadySent`） |
| `Ath10kHal.cpp` | `handleNewState` / `queueScanWork` / `runScanWork` / `scanCompletionAction` / `feedScanFrameTo80211` / `stageScanFrame` / `publishScan80211Properties` / `emitDriverReady`；`applyScanInfo` 改为暂存；`ath_newstate` 接线；`attach` / `enable` / `detach` / bring-up 收尾调整 |
| `tests/wmi-tlv-selftest.cpp` | 断言原始帧指针/长度、IE 偏移、`wmiFreqToChannel` 换算 |

### 3.3 `ath_newstate` 的行为

```cpp
case IEEE80211_S_SCAN:
    ic->ic_state = nstate;
    ieee80211_set_link_state(ic, LINK_STATE_DOWN);
    queueScanWork();          // 异步，立即返回
    return 0;                 // 不调用 net80211 的状态机
default:
    defaultNewState(ic, nstate, arg);   // INIT/AUTH/ASSOC/RUN 交回 net80211
```

SCAN 分支刻意**不**调用 net80211 的 `ieee80211_newstate()`（与 iwn 的做法一致）：
那会把状态机推进到 `ieee80211_begin_scan() → next_scan()` 的逐信道流程，
而我们是固件一次性全信道扫描，逐信道驱动只会打出无意义的状态轮转
（还会通过 `IEEE80211_SEND_MGMT` 往 `ic_mgtq` 里塞永远发不出去的 probe request）。

## 四、新增诊断属性

每轮扫描结束都会刷新（`publishScan80211Properties()`）：

| 属性 | 含义 |
| --- | --- |
| `ath10k-net80211-state` | `ic_state`（0=INIT 1=SCAN 2=AUTH 3=ASSOC 4=RUN） |
| `ath10k-net80211-opmode` | 应为 1（`IEEE80211_M_STA`） |
| `ath10k-net80211-nodes` | 当前 `ic_tree` 节点数（**扫描是否真的建了节点，看这个**） |
| `ath10k-scan-rounds` | 已完成的 WMI 扫描轮数 |
| `ath10k-scan-feed-attempts` | 尝试喂给 net80211 的帧数 |
| `ath10k-scan-feed-ok` | 成功进入 `ieee80211_input` 的帧数 |
| `ath10k-scan-feed-skipped` | 因不在 SCAN 状态被跳过的帧数 |
| `ath10k-scan-stage-overflow` | 暂存区放不下而丢弃的帧数 |
| `ath10k-scan-nodes` | 最近一轮结束时的节点数（与 `net80211-nodes` 同源） |
| `ath10k-scan-done-events` | 已发出的 `SCAN_DONE` 事件数 |
| `ath10k-scan-feed-status` | 最近一次喂帧/收尾的状态串（见下表） |

`scan-feed-status` 取值：

| 值 | 含义 |
| --- | --- |
| `fed` | 有帧成功喂入 |
| `round-complete-no-frames` | 扫描完成但固件没给管理帧 |
| `skipped-not-scan-state` | 收到帧时 `ic_state != SCAN`（多半是 DRIVER_READY 后系统没真正发起扫描） |
| `stage-overflow` | 帧太长/太多被丢弃 |
| `not-beacon-or-probe-resp` | 收到的是其它管理帧（正常现象，说明 MGMT_RX 通了） |
| `mbuf-alloc-failed` / `find-rxnode-failed` | 主机侧资源失败 |
| `pdev-setup-failed` / `chan-list-failed` | 前置 WMI 命令失败 |
| `timeout` / `complete-with-reason` / `aborted-detach` | 扫描本体失败 |

## 六、失败模式判读

| 现象 | 先看什么 | 结论 |
| --- | --- | --- |
| `feed-ok = 0`、`feed-status = skipped-not-scan-state` | `scan-rounds` 是否增长 | 扫描只在 `ic_state == SCAN` 时才收帧；如果 WCL 把状态推到 INIT，说明 `disable()` 被调用了（`setPOWER` 关），不是扫描问题 |
| `feed-ok = 0`、`feed-status = round-complete-no-frames` | `ath10k-scan-mgmt`、`ath10k-ce1-frames` | 固件没交帧（M1-c2 的 HTT 环问题），或本底噪太低扫不到；可先把 dwell 提到 300 ms |
| `feed-ok > 0` 但 `net80211-nodes = 0` | 系统日志里 `ath10k: SCAN BSS ...` 是否出现 | 帧进了 `ieee80211_input` 但被 net80211 丢弃：多半是信道一致性（DS 参数与 `rxi_chan` 不符）或缺 Rates/SSID IE |
| `nodes > 0` 但菜单无列表 | `scan-done-events` 是否 ≥ 1 | 没有 SCAN_DONE，WCL 认为扫描没结束（会 20 s 超时）；看 `ath10k-scan-feed-status` |
| `nodes > 0`、`done-events > 0`、菜单仍空 | `ath10k-scan-rounds` 是否每 ~15 s 增长 | 说明链路正常但 WCL 侧没显示，属于 M1-d（join / 射频状态上报）范围 |
| 开机 panic | `feedScanFrame` 相关栈 | 喂帧上下文错（必须在 workloop），或 `mbuf_allocpacket` 失败后仍继续用 m |

## 七、已知风险与后续

1. **扫描是持续循环的**：`end_scan` 找不到 AP 就会 `next_scan → newstate(SCAN)`，
   每轮约 13~15 秒。这与原生驱动"未连接时一直扫"的行为一致，但会持续占用一个
   thread_call 线程；M1-d 考虑把它降频（例如每 30 秒一轮）。
2. **`ieee80211_free_allnodes(ic, 0)` 每轮清节点**：保证列表只反映本轮，但
   `getSCAN_RESULT()`（非 WCL 构建）若正好在遍历时会看到空列表。真机上 macOS
   的扫描请求本来就会清缓存，所以可接受。
3. **dwell / 信道覆盖**：目前 22 个非 DFS 信道、fast dwell 200 ms。实测只有 2 帧
   MGMT_RX 到达，若要列表更丰富，建议下一轮把 dwell 提到 300~500 ms
   （`kWmiScanDwellMs` / `buildWMIStartScan(fast=false)`）。
4. **未处理定向扫描**：WCL 的 `scan.channelCount` / `scan.ssid` 目前被忽略，
   仍按全信道扫描。M1-d 一起做。
5. **连接流程未实现**：`ath_newstate` 的 AUTH/ASSOC/RUN 交回 net80211，
   但 `ath_start` / `ath_set_key` 还是空桩，真正连接要等 M1-d。
