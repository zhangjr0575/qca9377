# M0.1a 实现说明（硬件探测）

> 里程碑：M0.1a —— 在原生 AirPort 语境下证明能访问 QCA9377 硬件。
> 状态：代码完成、编译通过，待真机验证。

## 1. 目标

M0 已经证明「net80211 + AirportItlwm 控制器层能挂上 QCA9377 并发布原生 Wi-Fi 接口」，但**完全没有碰硬件**。M0.1a 要回答一个前置问题：

> 在 `IO80211Controller`/Skywalk 这条路径下，我们还能不能像 Ath10kMac 那样正常映射 BAR0、读芯片寄存器？

这是后续所有固件工作的基础。如果这里不通，整个路线 A 都要重新评估。

## 2. 做了什么

### 2.1 复用 Ath10kMac 的硬件抽象（零改动）

从 `Ath10kMac/src/kext/` 复制三个**完全自包含**的头文件到 `itlwm/itlwm/hal_ath10k/hw/`：

| 文件 | 作用 |
| --- | --- |
| `Ath10kHw.hpp` | PCI 设备 ID、芯片候选表、`isSupportedDevice`/`findCandidate` |
| `Ath10kTarget.hpp` | QCA6174/QCA9377 寄存器布局、`chipIdOffset`/`chipRevision` 等 |
| `Ath10kRegisterIO.hpp` | 带边界与对齐校验的 MMIO 读写抽象 |

三者仅依赖 `IOKit/IOLib.h` 与 `IOKit/IOTypes.h`，无需任何改造即可在 itlwm 中使用。

### 2.2 Ath10kHal 增加硬件探测

新增两个方法（`Ath10kHal.hpp/.cpp`）：

- `bool probeHardware()`：映射 BAR0、读取 `RTC_STATE` 与 `SOC_CHIP_ID`、匹配硬件候选。
- `void publishHardwareProperties()`：把结果写入 ioreg 属性，便于**无日志也能验证**。

关键设计取舍：

| 决策 | 原因 |
| --- | --- |
| 探测放在 `ieee80211_ifattach` **之前** | 后续里程碑要用真实 MAC 填充 `ic_myaddr`，顺序必须提前 |
| 全程**只读**，不写任何寄存器 | 避免在未掌握芯片状态机前操作硬件导致 panic |
| 探测失败**不阻断**接口发布 | M0.1a 失败不能让 M0 已验证的能力回退 |
| 日志统一改用 `IOLog` | itlwm 的 `XYLog` 用 `kprintf`，**不进 unified log**，M0 验证时已踩坑 |

### 2.3 发布的 ioreg 属性

```
ath10k-hardware-status   ok / chip-asleep / bar0-map-failed / chip-id-read-failed /
                         unsupported-chip-revision / unsupported-pci-device / no-pci-device
ath10k-chip-id           SOC_CHIP_ID 原始值
ath10k-chip-revision     芯片版本字段（bits[11:8]）
ath10k-bar0-length       BAR0 长度
ath10k-hw-probed         是否完成探测
ath10k-chip-name         芯片名（匹配成功时）
ath10k-target-revision   目标版本（如 hw1.1）
ath10k-firmware-dir      固件目录（如 QCA9377/hw1.0）
```

## 3. 验证方法

### 3.1 安装

产物：[`build/AirportItlwm-Sequoia-M0.1a.kext`](../build/AirportItlwm-Sequoia-M0.1a.kext)

替换 EFI 中的 kext（**注意：会删除旧 bundle，路径务必核对**）：

```sh
# 备份旧版
cp -R /Volumes/ESP/EFI/OC/Kexts/AirportItlwm-Sequoia.kext ~/Desktop/AirportItlwm-Sequoia-M0-backup.kext
# 替换
sudo rm -rf /Volumes/ESP/EFI/OC/Kexts/AirportItlwm-Sequoia.kext
sudo cp -R build/AirportItlwm-Sequoia-M0.1a.kext /Volumes/ESP/EFI/OC/Kexts/AirportItlwm-Sequoia.kext
```

重启后执行：

```sh
sh scripts/verify-m0.1a.sh
```

### 3.2 判读标准

| `ath10k-hardware-status` | 含义 | 下一步 |
| --- | --- | --- |
| `ok` | ✅ 硬件可访问、芯片识别成功 | 进入 M0.1b（唤醒+固件下载） |
| `chip-asleep` | 能读寄存器但读到 `0xffffffff`，芯片未唤醒 | M0.1b 先加 RTC 唤醒序列 |
| `bar0-map-failed` | IO80211 语境下无法映射 BAR0 | ⚠️ 严重，需评估是否需要显式 `open()` |
| `chip-id-read-failed` | BAR0 太小或偏移不可读 | 检查 BAR 长度与寄存器布局 |
| `unsupported-chip-revision` | 版本字段不在候选表 | 需补充硬件候选 |

**本机预期**：卡为 QCA9377 `hw1.1`（chip version 1），因此期望
`ath10k-chip-revision = 1`、`ath10k-target-revision = hw1.1`、`ath10k-hardware-status = ok`。

## 5. 已知限制

- 固件仍未启动，`getFirmwareVersion()` 返回 `"hw-probe"`。
- MAC 仍是占位值 `02:11:22:33:44:55`。
- 若 `bar0-map-failed`，说明需要在 `Ath10kHal` 侧显式打开 PCI 设备，属于 M0.1b 的前置修复项。
