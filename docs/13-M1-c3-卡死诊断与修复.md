# M1-c3 真机卡死：诊断与修复（r1）

> 现象：部署 M1-c3 构建后开机正常，进入桌面约 1~2 分钟后整机无响应（无 panic 报告、
> 无画面输出、必须硬断电）。上一版（M1-c2b）不会卡死。
> 时间：2026-11-17

---

## 一、复述现象

- 三次重启均复现：能进桌面 → 1~2 分钟后整机冻结；
- 冻结后连 `sh scripts/verify-m1c3.sh` 都无法执行（无终端响应）；
- `/Library/Logs/DiagnosticReports` 里**没有** panic 报告（最后一份是 11-16 23:26 的
  shutdown stall），说明是**硬挂死**而不是 panic 重启。

## 二、代码层面确认的两个事实（读 xnu 源码）

1. `IOWorkLoop::runAction()` 的实现是
   `closeGate(); inAction(...); openGate();`
   —— action **在调用者线程上执行，但全程持有 workloop 的递归锁**，
   并不会切到 workloop 线程。所以 r0 版本里"切到 workloop 再喂帧"实际上是把
   整个 net80211 + WCL 回调放进了 workloop 锁内执行。
2. `IOCommandGate::runAction()` 同样是"closeGate 后**原地**执行 action"；
   只有 gate 被 disable 时才 `sleepGate`。所以 `if_input()` 内部那层
   `_fCommandGate->runAction()` **不会切换线程**，也不会因为"线程不同"而死锁
   （gate 递归、默认 enabled）。**结论：r0 不是锁死，这一点要纠正。**

那 r0 的问题是什么？两件事叠加：

- `scanCompletionAction` 把 16 帧 `ieee80211_input` → `ic_event_handler(BEACON)`
  → `WCL publishWCLBeacon` → `postMessage` 全部放进了 **workloop 锁内**
  （r0 用的是 `IOWorkLoop::runAction`）。注意 iwx/iwn 的 RX 是在 workloop 的
  中断事件源里跑的（同样持锁），所以"持锁喂帧"本身不算违例；
  但它把一个**可能很慢**的整段串行工作放进了锁内，属于不必要的长临界区，
  一旦 `postMessage`/net80211 侧有任何阻塞点，整个网络栈（乃至依赖它的系统
  服务）会一起卡住。
- 更关键的是第三节的自旋：它让上述长临界区在**毫秒级**反复发生。

## 三、更可能的真凶：`end_scan → next_scan` 形成了**无间隔自旋**扫描环

r0 每轮扫描结束都会调用 `ieee80211_end_scan()`。它的 `notfound` 分支是：

```
ieee80211_reset_scan → ieee80211_next_mode → ieee80211_setmode
→ ieee80211_next_scan → ieee80211_new_state(SCAN) → ath_newstate
→ queueScanWork → 下一轮 START_SCAN
```

而 `runWMIScan()` 在 **提交失败**（例如 CE3 判为污染、`wmiTxFail = ce3-not-idle`）
或前置命令失败时是**立即返回**的，不会消耗 12 秒的收集窗口。于是：

- 成功路径：每轮 ~13 s，尚可；
- 失败路径：`submit 失败 → end_scan → 立刻重排 → 再 submit 失败 ……`
  **毫秒级无限循环**，每轮还要做
  `ieee80211_free_allnodes()`、`publishHardwareProperties()`（约 150 次
  `setProperty`）、若干 `IOLog`、以及 `thread_call` 反复 enter。

这种循环会持续抢占 IOKit 注册表锁与 unified log 锁，几十秒内即可拖死整机，
且**不会留下 panic**——与观察到的现象一致。首次扫描通常没问题（所以前 30 秒正常），
一旦某轮 START_SCAN 的 CE3 事务没被消费或扫描事件丢了，就进入自旋。

## 四、修复（r1）

原则：**把"持续扫描"改成"按系统请求扫描"，任何失败都必须退避，绝不允许自旋。**

| 改动 | 说明 |
| --- | --- |
| 不再调用 `ieee80211_end_scan()` | 只发 `IEEE80211_EVT_SCAN_DONE` 事件（WCL 需要的就是这一个）。不再触发 `next_scan` 的逐信道重扫、也不会误入 AUTH/ASSOC 分支 |
| 新增 1 Hz `IOTimerEventSource` 驱动轮询 | 开机只跑 **1 轮**无条件扫描（证明通路 + 列表有内容），之后只在 `ic_wcl_scan_requested` 为真时开新一轮；同一个系统请求最多 2 轮（覆盖 WCL 的 `scanSkipCompletion` 需要两次 SCAN_DONE 的情形） |
| 两轮之间强制 ≥10 s 间隔，失败退避 | 失败后 5 s 起，按连续失败次数线性退避，上限 35 s |
| **连续 3 轮失败自熔断** | 直接把 `scanDisabled` 置位（`ath10k-scan-self-fused=1`），彻底停止扫描——最后一道保险 |
| 单轮收集窗口 12 s → 8 s，收尾 2 s → 1.5 s | 缩短单轮最坏暴露时间（实测一轮约 1 s 就完成） |
| 喂帧不再经过 workloop 锁 | 直接在扫描线程里 `mbuf + find_rxnode + ieee80211_input`，与 iwx 的 RX task 上下文一致（`if_input` 的 `_fCommandGate->runAction` 会自行加锁） |
| 每轮只发布轻量属性 | `ath10k-scan-bss*` / `ssids` / 计数；完整的 `publishHardwareProperties()` 只在 bring-up 结束时做一次（每轮 ~150 次 `setProperty` 太贵） |
| 日志降噪 | 扫描事件/BSS 明细只在第 1 轮打印，之后每轮一行摘要 |
| boot-arg 熔断开关 | `ath10k_scan=0` 可整体关闭 M1-c3 扫描（`ath10k-scan-disabled=1`），用于在不重编的情况下排除扫描因素 |

### 4.1 顺带修掉的一个隐形炸弹（部署脚本已加固）

r1 开发途中出现过"声明了 `publishScanResultsProperties()` 但没有定义"的情况：
**kext 链接器不会报错**（kext 允许未定义符号，留待内核在加载时解析），
`xcodebuild` 依然 `BUILD SUCCEEDED`，但产物里该符号是 `U`（undefined），
重启后驱动根本不会加载。现在 `scripts/deploy-kext.sh` 会检查：

```sh
nm -u -C <kext 二进制> | grep -E "Ath10kHal|AirportItlwm::"   # 必须为空
```

非空时直接 `exit 1`，不会再出现"部署成功但驱动没加载"的黑盒。

### 4.2 r1 第二轮加固（复核后追加）

复核发现"按请求扫描"还不够，又补了三条硬约束：

| 加固 | 目的 |
| --- | --- |
| **开机 60 s 静默期**（`kScanGraceTicks`） | 这段时间内任何扫描请求都不执行。留出"驱动已加载但完全不扫"的观察窗口，把 r0 卡死定性成"装载/接线问题"还是"扫描/喂帧问题" |
| **`kScanInitialRounds = 0`** | 开机不再自动扫。第一次扫描必须由系统请求（打开 Wi-Fi 菜单 / `airport -s`）触发，即完全可控 |
| **通路级失败立即熔断** | `ce3-*` / `no-credit` / `doorbell` / `rx-arm` / 前置命令失败 → 立刻 `scanDisabled`（不再退避重试）。只有 `timeout`、`complete-with-reason` 这类软失败允许重试 |
| **卡轮看门狗** | `scanWorkRunning` 超过 40 s → 判定卡死，停掉调度并留日志（线程本身若卡在 MMIO 里无法挽回，但至少不再叠加新工作） |
| **失败计数/请求轮数入属性** | `scan-fail-streak`、`scan-request-seen`、`scan-request-rounds`、`scan-round-start-tick`，冻结后重启即可反推停在哪一步 |

### 预期行为（r1）

- 开机后：bring-up ≈15 s → **60 s 静默期**（`scan-rounds = 0`，
  `scan-feed-status = "waiting-grace-window"`）→ 静默期结束后，只有系统发起
  扫描请求才扫，1~2 轮（每轮 ≈1~8 s，间隔 ≥10 s）；请求标志被 WCL 清掉后
  再次静止；
- 任一轮失败：进入 5~35 s 退避，`ath10k-scan-fail-streak` 递增，
  `ath10k-scan-feed-status` 保留失败原因；
- 卡死风险点（自旋、锁内长阻塞、日志洪泛）均已消除。

> ```sh

1. 部署 r1，重启，等 60 s；

   ```sh

   ```

   期望：`scan-rounds = 0`、`scan-feed-status = "waiting-grace-window"`、
   `scan-self-fused = 0`、`scan-disabled = 0`、`hardware-status = "wmi-ready"`。
   **这一步就是在验证"驱动加载 + 空闲"不会卡死。**
3. 观察 3~5 分钟（仍不开 Wi-Fi 菜单）：`scan-rounds` 必须保持 0 不动。
   **如果它开始增长或出现别的异常，立刻回报**

   `scan-feed-ok > 0`，`airport -s` 里出现 SSID。
5. 再静置 5 分钟：`scan-rounds` 必须停住（每个系统请求最多 2 轮）。

## 五之五、r1 真机结果（2026-11-17 22:29）：系统不卡了，真正的 Bug 现形

r1 部署后：开机 6 分钟**完全稳定**，自旋消失（`scan-rounds` 停在 1 不再增长），
熔断按设计生效。同时暴露了被 r0 的自旋掩盖的真正故障：

```
ath10k-scan-rounds        = 1
ath10k-scan-request-seen  = 1
ath10k-scan-round-start-tick = 60      ← 正好在静默期结束那一刻
ath10k-scan-feed-status   = "ce3-not-idle"
ath10k-scan-self-fused    = 1          ← 第一次致命失败就熔断
ath10k-scan-events        = 0          ← START_SCAN 根本没提交出去
ath10k-net80211-nodes     = 0
```

### 根因：CE3 的"空闲"判定用了寄存器原始值，而固件会改写读索引

`wmiSubmitCommand()` 的预检原来是：

```cpp
snap.srcWriteIndex >= entries || snap.currentSrcRead >= entries ||
snap.srcWriteIndex != snap.currentSrcRead      // ← 原始值直接相等
```

但 CE 的 `currentSrcRead` 是**自由计数**（Linux ath10k 侧一律
`read_index & (nentries - 1)` 后再比较），而且固件在 WMI INIT / vdev 之后会
自己改写它。于是：

- M1-c1 能扫，是因为扫描命令**紧跟** SCAN_CHAN_LIST 提交，索引还是我们刚写下的 5/5；
- M1-c3 把扫描改成 45~60 s 之后异步执行，读索引早已被改写 → 预检判"not idle"
  → 提交失败；
- r0 又在失败后立刻 `end_scan` → 重扫，于是**同一个失败**被毫秒级重复 →
  整机卡死。

这条链把之前所有现象都解释通了：为什么 C1 能扫到真实 SSID、为什么 r0 一进桌面
一两分钟就死、为什么 `vdev-ok`/`wmi-init-ok` 一直正常。

### r2 修复

| 改动 | 说明 |
| --- | --- |
| 索引一律取模后再比较 | 与成功路径 `(srcRead & (entries-1)) == next` 保持一致，兼容自由计数 |
| **CE3 重同步** | 当写≠读、但驱动账本确认"无在途命令"（`!wmiTxOwned || wmiTxConsumed`）时，把设备读索引当作新的写位置继续提交，并递增 `ath10k-ce3-resyncs` 留痕 |
| 仍在途则硬失败 | 账本说有条命令没落地时绝不重同步（`ce3-not-idle`），防止踩掉在途描述符 |
| 失败原因拆细 | `ce3-snapshot` / `ce3-structure` / `ce3-not-idle` / `ce3-byteswap` / `ce3-resync`，不再一律叫 not-idle |
| 结构校验分级 | 环基址/长度/字节序不符才硬失败；`dmax`（突发长度）被固件改动只记录不拦 |
| WMI TX 诊断每轮刷新 | 之前 `ath10k-wmi-tx-fail` 只在 bring-up 发布，判读时看到的是旧值 `"none"`，误导过一次；现在连同 raw 索引一起每轮刷新 |

## 五之六、r2 真机结果（2026-11-17 22:55）：`0xDEADBEEF` —— SOC 睡下去了

r2 把失败原因拆细后，一次就拿到了决定性数据：

```
ath10k-wmi-tx-fail          = "ce3-structure"
ath10k-wmi-tx-src-write-raw = 3735928559   ← 0xDEADBEEF
ath10k-wmi-tx-src-read-raw  = 3735928559   ← 0xDEADBEEF
ath10k-ce3-resyncs          = 0
```

`0xDEADBEEF` 正是 docs/05 记录的**"芯片未唤醒"哨兵值**（`SOC_CHIP_ID` 在
冷复位前就读回它）。也就是说：CE3 的整个寄存器窗口都读不到真值，
**SOC 在 bring-up 结束后睡下去了**，而固件只是"曾经"跑起来过。

根因在 bring-up 收尾：

```cpp
finish:
    releaseTargetWake();   // 清 SOC_WAKE
    restoreASPM();         // 恢复 ASPM
```

M0/M1-b2 阶段这样写没问题（那时只要求"探测完把芯片放回去"），但**一旦固件在跑**，
就必须像 Linux 的 `ath10k_pci_power_up()` 那样**一直保持 SOC_WAKE 断言**，
只在 `power_down()`（驱动 detach / 休眠）时释放。提前释放 → SOC 空闲后睡眠 →
之后所有 CE 寄存器读都是 0xDEADBEEF。

这也再次解释了历史现象：M1-c1 的扫描之所以能拿到真实 SSID，是因为它跑在
bring-up **内部**，那时 `SOC_WAKE` 还断言着。

### r3 修复

| 改动 | 说明 |
| --- | --- |
| **bring-up 成功后不再释放唤醒** | 固件跑起来（`wmiVdevOk`）就保持 `SOC_WAKE` 断言 + ASPM 关闭，只在 `detach()` 收尾（对齐 Linux power_up/power_down 语义） |
| `ensureTargetAwake(stage)` | 运行期每次扫描前读 `RTC_STATE`；不是 ON 就重新断言 `SOC_WAKE`（必要时先关 ASPM）并递增 `ath10k-wake-retries` |
| CE3 哨兵识别 | 索引/ctrl1 读到 `0xDEADBEEF`/`0xFFFFFFFF` 时直接定性为 `ce3-asleep`（不再是含混的 `ce3-structure`） |
| 单次重试 | 只有 `ce3-asleep` 允许"唤醒后重提一次"（此时提交根本没发生，CE3 未被污染） |
| 新属性 | `wake-asserted` / `target-awake` / `wake-retries` / `last-rtc-state` / `last-rtc-readable` |

## 五之七、r3 真机结果（2026-11-17 23:09）：扫描彻底打通，只差最后一步接线

```
scan-rounds = 12   scan-feed-ok = 174   scan-mgmt = 19   scan-bss-count = 16
net80211-nodes = 15   feed-status = "fed"   self-fused = 0   wake-retries = 0
scan-bss0..7 = ChinaNet-YD / Xiaomi_09FA / CMCC-t2Zt / OnePlus 13T 55FE / ...
```

- **系统稳定**（5 分钟无异常，`scan-rounds` 不再自旋）；
- **驱动侧扫描与喂帧全部成功**，真实 SSID 出现在 ioreg；
- 但 `scan-done-events = 0`，`airport -s` 仍然为空 → 系统侧还差一根线。

### 根因：`bzero(&ic)` 抹掉了 `start()` 预先设置的 `ic_event_handler`

`AirportItlwm::start()` 的顺序是：

```cpp
fHalService->initWithController(this, _fWorkloop, _fCommandGate);
fHalService->get80211Controller()->ic_event_handler = eventHandler;   // ← 先写
...
if (!fHalService->attach(pciNub)) { ... }                             // ← 后 attach
```

而 `Ath10kHal::attach()` 开头有 `bzero(&ic, sizeof(ic));` ——
把 `ic_event_handler`（以及 boot-arg 写入的 `ic_userflags`）一起清成 0。
结果：

- 我们喂帧时 `ic.ic_event_handler == NULL` → net80211 不发 `IEEE80211_EVT_BEACON`
  → WCL 收不到 `publishWCLBeacon` → 系统扫描结果永远为空；
- `runScanCompletion()` 里的 `SCAN_DONE` 也因同一条件不成立而不发
  （`scan-done-events` 一直是 0）；
- `emitDriverReady()` 每次都认为"handler 还没装"，`DriverAvailable` 也从未上报。

### r4 修复

| 改动 | 说明 |
| --- | --- |
| `attach()` 备份/恢复 `ic_event_handler` 与 `ic_userflags` | 在 `bzero(&ic)` 之后立刻写回，保留 `start()` 的预设值 |
| 轻量发布补 `net80211-event-handler` | 直接暴露"WCL 事件回调是否挂上"，一眼可判 |
| 轻量发布补 wake/RTC 字段 | r3 判读时这几项还是 bring-up 的旧值（又一次"旧值陷阱"） |
| 暂存区 16×768 → 32×1024 | 实测每轮约 19 帧，旧上限截断了 39 帧 |

## 六、如果仍然卡死

按顺序用 boot-arg 熔断缩小范围（在 OpenCore `boot-args` 里加）：

| boot-arg | 作用 | 判读 |
| --- | --- | --- |
| `ath10k_scan=0` | 完全不排队扫描 | 若仍卡死 → 与扫描无关（是 `ic_newstate` 接管 / `IFF_RUNNING` / `DRIVER_READY` 引入的） |
| 去掉 `ath10k_scan=0`，保留扫描 | — | 若卡死 → 扫描 / 喂帧路径 |

另外冻结后重启第一时间检查（这三条能区分"panic 重启"和"硬挂死"）：

```sh
nvram -p | grep -i panic
ls -lt /Library/Logs/DiagnosticReports | head
sudo log show --last 30m --predicate 'eventMessage CONTAINS "Ath10kHal"' --style compact | tail -40
```

最后一条最关键：r1 每轮只打一行
`Ath10kHal: M1-c3 scan round=N ok=... status=... nodes=...`，
日志最后停在第几轮、`status` 是什么，就能直接判断卡在扫描前/扫描中/喂帧后。
`log show` 需要 sudo（本会话的沙箱不允许，需要你手动执行）。
