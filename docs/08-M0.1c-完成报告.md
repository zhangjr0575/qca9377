# M0.1c 完成报告：QCA9377 固件在原生 AirPort 路径下成功启动

> 时间：2026-11-16 21:27
> 结论：**M0.1c 全链路打通，QCA9377 固件在 itlwm/AirportItlwm 原生 WiFi 路径下成功运行。**

## 1. 最关键的结果

```c
ath10k-htc-ready-ok      = 1
ath10k-htc-status        = "htc-ready"
ath10k-htc-rx-bytes      = 20      // 固件发来的第一个 HTC 包
ath10k-htc-wait-ms       = 3
ath10k-htc-credits       = 2
ath10k-htc-credit-size   = 1792
ath10k-htc-endpoints     = 4
ath10k-htc-version       = 1
ath10k-htc-parse-error   = "none"
ath10k-htc-fw-indicator  = 0x00000002   // initialized，bit0 未置（无崩溃）
ath10k-bmi-done-sent     = 1
ath10k-bmi-closed        = 1
```

`BMI_DONE` 发出后 3 毫秒固件就回了 HTC READY，说明固件已完整初始化并进入 HTC 服务阶段。

## 2. 一个强正确性证据

```
ath10k-boot-hi-option-applied      = 0x00002208   （我们写入）
ath10k-hi-option-after-download    = 0x0000220a   （固件改为）
```

固件启动后主动把 `HI_OPTION_BMI_CRED_LIMIT`(bit1) 追加进去。Ath10kMac 源码注释明确记录过同一现象：

> "Hardware testing of 0.0.20 observed this flag become set after OTP/WLAN loading (0x2208 -> 0x220a)."

**我们的实现与参考实现在真机上观察到了逐位一致的行为**，这是比日志更硬的正确性证据。

## 3. 完整链路回顾

```
PCI BAR0 映射
  → 芯片识别 SOC_CHIP_ID=0x003821ff (hw1.1)
  → 唤醒 + 冷复位
  → CE ring ×6 分配（含 64 KiB CE4，历史坑已绕过）
  → 热复位（3 遍 CE 管道编程）
  → CE7 诊断通道（读写 target 内存）
  → init_config 写入（pipe_cfg 168B + svc_map 204B + HI 字）
  → CPU 唤醒 CORE_CTRL |= 0x2000
  → BMI 协议（GET_TARGET_INFO = 0x05020001）
  → HI 前置探测 + 176 MHz PLL + Boot HI 五字
  → board data 8124B 上传 + 回读
  → OTP 24193B LZ 下载 + BMI_EXECUTE
  → WLAN 固件 727125B LZ 下载 + 6 段回读（727053B 全对）
  → Boot HI 收尾（关 UART）
  → CE1 挂 2048B RX
  → BMI_DONE
  → HTC READY ✅
```

## 6. 复用过程中遇到的真实差异

| 问题 | 原因 | 处理 |
| --- | --- | --- |
| `PLLClock::div` 编译失败 | 与 libc `div()` 同名 | 改名 `divider` |
| `PLLClock::hz` 编译失败 | itlwm 的 `_clock.h` 有 `#define hz 100` | 改名 `freqHz` |
| `hi_board_data_initialized` 一直为 0 | 该标志由 **host 主动写入**，不是等 ROM 置位 | 改为写后回读验证 |
| 固件 LZ 未启动 | 前置条件 `otpResultAccepted` 漏了 `!` | 修正并加自解释日志 |
