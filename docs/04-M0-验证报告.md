## 3. 重要发现：3 个 kernel panic 与本项目无关

系统中存在 3 个 panic 记录，**均来自旧的 `br.com.jonasw8.driver.ath10kmac` kext，不是本项目的 AirportItlwm**。

### 3.1 崩溃点完全一致

| panic 文件 | 时间 | 崩溃栈 |
| --- | --- | --- |
| `Kernel-2026-11-15-215526.panic` | 11-15 21:55 | `Ath10kAirport::start()` ← `Ath10kPCIDevice::createAirportService()` |
| `Kernel-2026-11-15-224156.panic` | 11-15 22:41 | `Ath10kAirport::start()` ← `Ath10kPCIDevice::createAirportServiceCall()` |
| `Kernel-2026-11-16-110103.panic` | 11-16 11:01 | `Ath10kAirport::start()` ← `Ath10kPCIDevice::createAirportServiceCall()` |

崩溃性质：`type 14 = page fault`，`RIP = 0xffffff8046600000`（未映射地址），说明**跳转到了一个空/非法函数指针**——即在 `Ath10kAirport::start()` 里调用了未正确初始化的虚函数。

### 3.2 说明

- 此前已存在一次“在 Ath10kMac 里直接做原生 AirPort”的尝试（对应路线 B），并因空指针调用而崩溃。
- 该 `Ath10kAirport` 代码**未出现在工作空间 git 历史中**（`git log -S "Ath10kAirport"` 无结果），说明是在 EFI 或另处临时实验，未提交，现已丢失。
- 本次启动中旧 `ath10kmac` kext **已不在加载列表**，说明已从 EFI 移除，不存在两个 kext 抢占同一 PCI 设备。
- **这条经验反过来验证了路线 A（net80211）的选择**：直接新写 IO80211Controller 会让厂商私有的 Airport 类生命周期极难正确初始化，而我们复用 AirportItlwm 成熟的控制器层规避了该类问题。

## 4. 已知限制（M0 范围内，符合预期）

- MAC 为占位值 `02:11:22:33:44:55`，非真实 OTP MAC。
- `en4` 状态 `inactive` / `Not Associated`：无扫描、无连接、无数据面。
- Wi-Fi 菜单点击后不会有真实网络列表（`ath_newstate` 为空桩）。
- 固件实际未启动，`fw: 1.0.0-alpha` 是硬编码字符串。
