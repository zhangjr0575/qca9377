## 一、目标与拆分

**目标**：能在 Wi-Fi 菜单里选中一个网络并真正连上（先 WPA2-PSK，再开放网络）。

M1-d 拆成 4 个增量，每个都能单独验证、且默认不影响已然稳定的扫描/菜单路径：

| 增量 | 内容 | 状态 |
| --- | --- | --- |
| d-1 | 连接命令帧 + HTT TX 描述符 + 离线自测 | ✅ 本次完成（`hw/Ath10kWmiConnect.hpp`） |
| d-2 | `ath_newstate` AUTH/RUN 接上命令链；`ath_start` 用 HTT TX 发认证/关联帧；运行期 RX 泵；MGMT_RX 放行 auth/assoc/deauth | ✅ 已实现（`build/AirportItlwm-Sequoia-M1d1.kext`，待真机验证） |
| d-3 | `ath_set_key` / RSN 四步握手（WMI SET_KEY）+ EAPOL 走数据面 | ⏳ |
| d-4 | 中断化（MSI）替代 CE 轮询；去掉 60 s 静默期等临时措施 | ⏳ |

## 二、关键机制（读 Ath10kMac 参考实现确认）

1. **QCA9377 固件不做 SME**。固件不会自己发 auth/assoc，必须由主机构造 802.11
   管理帧并通过 **HTT TX（CE4）** 发出；响应从 **WMI MGMT_RX（0x7001）** 上来
   （M1-c1 的解析器已经在处理这个事件）。
2. 连接命令走 **WMI（CE3）**，顺序固定：

```
VDEV_START(0x5003)     带 SSID + 信道 + phy mode + 功率
  → PEER_CREATE(0x6001)      以 AP 的 BSSID 建 peer
  → PEER_ASSOC(0x6005)       把协商结果（rates / HT / VHT / aid / caps）交给固件
  → [HTT TX] 发 AUTH 请求 → 收 AUTH 响应
  → [HTT TX] 发 ASSOC 请求 → 收 ASSOC 响应
  → PEER_SET_AUTHORIZE(0x6004)  param 3 = 1
  → VDEV_UP(0x5005)           带 AID + BSSID
  → [WMI SET_KEY] 装 PTK/GTK → 4-way handshake → port authorized
```

3. 参考实现的字节布局（**必须逐字沿用**，都是真机试出来的）：
   `Ath10kMac/src/kext/Ath10kConnection.hpp`
   - `buildConnectionWMI()`（约 580~660 行）：VDEV_START / PEER_* / VDEV_UP
   - `buildStationManagement()`（约 779 行）：AUTH / ASSOC 请求帧
   - `buildHTTPacket()`（约 1427 行）：HTT TX 描述符
   - `submitNetworkPacket()`（`Ath10kNetwork.cpp:561`）：CE4 提交 + TX 完成回收

## 四、d-2 前必须补的一个结构性缺口：运行期 RX 泵

M1-c3 的收帧时机是**扫描期间**：`runWMIScan()` 在轮询 CE2/CE1 时顺带把 MGMT_RX
喂给 net80211。但连接流程不同——auth/assoc 响应、EAPOL、后续数据帧都在
**扫描结束之后**才到达，那时没有任何人在泵 CE2/CE1，帧就会躺在环里。

所以 d-2 必须先加一个**运行期 RX 泵**：

- 位置：优先挂在已有的 1 Hz 定时器之外，用一个 2~5 ms 的 thread_call 循环
  （或复用扫描 worker 的空闲期），只在 `ic_state >= AUTH` 时工作；
- 职责：`wmiPumpOnce()`（CE2 事件 + CE1 HTT 消息）→ MGMT_RX 帧交给
  `feedScanFrameTo80211()`（改名 `feedMgmtFrameTo80211`）；HTT 0x0e/0x0b 完成事件
  交给 TX 回收；
- **有界**：每次泵最多处理 N 个包就退出，绝不允许像 r0 那样无退避自旋；
- 与扫描 worker 互斥：同一时刻只允许一个泵（`rxPumpRunning` 标志）。

## 四之二、d-2 的实现要点（下一步）

0. **认证/关联帧不用我们构造**：net80211 的 `ieee80211_send_mgmt()` 已经把完整帧
   （含 SSID / rates / RSN IE）放进 `ic->ic_mgtq`，之后调 `if_start`。
   `ath_start()` 只需 `mq_dequeue(&ic->ic_mgtq)` 取出、拷进 TX DMA、
   `buildHTTPacket(mgmt=true)`、CE4 提交，并等 HTT `MGMT_TX_COMPLETION`(0x0e)
   ——所以 `buildAuthRequest` / `buildAssocRequest` 只作离线自测与兜底，不必上机。
1. `ath_newstate`：
   - `IEEE80211_S_AUTH`：先确认 `ensureTargetAwake()`，提交 VDEV_START → PEER_CREATE
     → PEER_ASSOC（每步等 WMI 回复/信用归还），然后让 net80211 发 AUTH 请求（它会
     调用 `ic_send_mgmt` → `if_start`）。
   - `IEEE80211_S_ASSOC`：等待 AUTH 响应成功（net80211 自己会推进），提交
     PEER_SET_AUTHORIZE。
   - `IEEE80211_S_RUN`：提交 VDEV_UP，并把 `ic_bss` 的 AID/BSSID 带进去。
2. `ath_start`：从 `ic->ic_mgtq` 取帧 → 拷进 TX DMA buffer → `buildHTTPacket(mgmt=true)`
   → CE4 提交 → 等 CE4 消费 → 等 HTT `MGMT_TX_COMPLETION`（HTT 消息类型 0x0e）。
3. MGMT_RX 放行：现在 `stageScanFrame` 只收 beacon/probe-resp；要扩成
   `auth / assoc resp / deauth / disassoc / action`，否则 net80211 的状态机不会前进。
4. 失败必须"自解释 + 不重试"：CE4 提交失败/完成超时只记状态并回退到 SCAN，
   绝不重排（r0 卡死的教训）。

## 四之三、d-2 实现清单（本次）

| 位置 | 内容 |

## 四之五、第一次真机验证（M1d1）：连接请求根本没到驱动

`build/AirportItlwm-Sequoia-M1d1.kext` 部署后：菜单点选网络 → 连接失败，
但驱动侧 `join-stage=0 / join-commands=0 / mgmt-tx-submitted=0 / rx-pump-running=0`，
`join-status` 仍是初始值 `"not-run"`。**新代码一行都没跑到**。

原因在 WCL 的连接入口 `startWCLJoin()`：

```cpp
if (!supported || !(ic->ic_if.if_flags & IFF_RUNNING) || joinPending || scanPending) {
    explicit_bzero(&join, sizeof(join));
    return !supported ? kIOReturnUnsupported : kIOReturnBusy;   // ← 静默失败
}
```

四道门槛任何一条不满足都只是返回错误码，驱动侧完全不可见。
另外还有一个**我自己设计上的漏洞**：连接触发只挂在"扫描轮结束"上，
而用户点选网络的时刻可能根本没有扫描在跑 → `end_scan` 永远不被调用。

### M1d2 的修正

| 改动 | 说明 |
| --- | --- |
| **独立连接触发** | 新增 `checkJoinTrigger()`：1 Hz 节拍检查 `ic_wcl_join_requested`/`ic_des_esslen`，且 `hasJoinTarget()`（`ic_tree` 里已出现目标 AP）时排一次 worker 执行 `ieee80211_end_scan()`，不再依赖扫描轮 |
| 重试限速 | 触发间隔 ≥10 s，失败后不会重演 r0 的自旋 |
| 触发后停扫 | `joinTriggered` 期间跳过扫描调度，避免与连接竞争；回到 SCAN 态自动复位 |
| WCL 入口可观测 | `startWCLJoin()` 每个分支都 `IOLog` + 把原因写到控制器的 `wcl-join-last-result`（`unsupported/no-running/scan-pending/join-pending/deferred-mac-reconfig/accepted`），并统计 `wcl-join-attempts` |
| HAL 侧暴露 | `wcl-join-requested`、`wcl-scan-requested`、`wcl-mac-reconfig`、`des-esslen`、`if-running`、`if-flags`、`ic-flags` |

产物：`build/AirportItlwm-Sequoia-M1d2.kext`（md5 `d0313669647b7035c163e94b8fc6e756`）。

## 四之六、第二次真机验证（M1d2）：真正的拦路者是 `ic_wcl_mac_reconfig`

M1d2 暴露了决定性数据：

```
ath10k-if-running          = 1      ← IFF_RUNNING 正常（ifconfig 不显示不代表没置位）
ath10k-wcl-join-requested  = 0
ath10k-des-esslen          = 0
ath10k-wcl-scan-requested  = 0      ← 系统连扫描都不再请求了
ath10k-wcl-mac-reconfig    = 1      ← ★ 关键
wcl-join-attempts          = （不存在）→ startWCLJoin() 一次都没被调用
```

### 机制

`AirportItlwm::setHardwareAddress()`（WCL 给接口下发随机 MAC 时调用）：

```cpp
if (ic->ic_if.if_flags & IFF_RUNNING) {
    ic->ic_wcl_mac_reconfig = true;       // 置位，等驱动回一条 DRIVER_READY
    fHalService->disable(bsdInterface);
    fHalService->enable(bsdInterface);
}
```

WCL 侧只有收到 `IEEE80211_EVT_DRIVER_READY` 才会：

```cpp
if (AirportWCL::consumeMacReconfiguration(ic->ic_wcl_mac_reconfig, ready)) {
    if (ready) resumeWCLJoin();
    break;                                 // 注意：这种情况下不再发 DriverAvailable
}
```

我们只在开机发过一次 `DRIVER_READY`（`driverReadySent` 一次性），所以 MAC 轮换之后
`ic_wcl_mac_reconfig` **永久卡在 1**，于是：

- `DRIVER_RESET_BEGIN` 被 `break` 掉，不再向系统发 `ResetInterface`；
- `startWCLJoin()` 把点击当成"延后请求"吞掉，等一个永远不会来的确认；
- 系统侧连扫描请求都不再下发（`ic_wcl_scan_requested` 一直是 0）；
- 驱动侧所有计数保持 0 —— 于数据完全吻合。

### M1d3 修正

| 改动 | 说明 |
| --- | --- |
| `emitDriverReady(bool force)` | 允许在 `driverReadySent` 之后再次发送（只用于 MAC 重配置确认） |
| 1 Hz 节拍补发 | `scanTick()` 最开头（早于静默期/扫描熔断/状态判断）检查 `ic.ic_wcl_mac_reconfig`，置位就补发一条 `DRIVER_READY`，至少隔 2 s、最多 8 次，避免风暴 |
| 确认后复位 | 标志被 WCL 清掉后打印确认日志并把计数归零，下一次 MAC 轮换可再次确认 |
| 诊断 | 新增 `ath10k-mac-reconfig-acks`，配合 `wcl-mac-reconfig` 一起看 |

产物：`build/AirportItlwm-Sequoia-M1d3.kext`（md5 `d0c1208760ddcf163e91a76fecd3f5a6`）。

## 四之七、第三次真机验证（M1d3）：握手修好了，但定向扫描被"吞掉"

M1d3 结果：`wcl-mac-reconfig = 0` ✅、`wcl-scan-requested = 1` ✅（系统恢复交互），
但 `wcl-join-attempts` 仍然不存在、`wcl-join-requested = 0`。

根因在 WCL 的 `SCAN_DONE` 处理：

```cpp
case IEEE80211_EVT_SCAN_DONE:
    if (scanPending) {
        if (scanSkipCompletion)
            scanSkipCompletion = false;          // ← 定向扫描的 SCAN_DONE 被吞掉
        else { scanCompleted = true; scanSource->setTimeoutMS(0); }
    }
```

点选网络时 macOS 发的是**定向扫描**（`ic_wcl_scan_ssid_length != 0`），
`beginWCLScan()` 会把 `scanSkipCompletion` 置真，于是：

1. 我们扫完并发完 ScanResult，SCAN_DONE 被吞 → 系统这次扫描请求不结束；
2. 只能等 `scanSource` 的 20 s 超时 → `finishWCLScan(kIOReturnTimeout)`；
3. macOS 判定扫描失败，**从此不下发 JOIN**；
4. 而即便 JOIN 来了，`startWCLJoin` 里 `scanPending` 仍为真 → 直接 Busy。

死路闭环。iwx 之所以没暴露，是因为它的扫描收尾会走 `ieee80211_end_scan()`，
而本驱动的扫描收尾路径与它不同（M1-c3 为避免自旋故意不调 end_scan）。

### M1d4 修正

| 改动 | 说明 |
| --- | --- |
| SCAN_DONE 一律收尾 | 去掉 `scanSkipCompletion` 的吞掉逻辑：任何 SCAN_DONE 都 `scanCompleted = true; scanSource->setTimeoutMS(0)`，让系统这次扫描请求正常结束 |
| JOIN 抢占扫描 | `startWCLJoin()` 若发现 `scanPending`，直接 `finishWCLScan(kIOReturnAborted)` 后继续，绝不再返回 Busy（消除竞态） |
| 拒绝原因收敛 | 只剩 `unsupported` / `no-running` / `join-pending` 三种 |
| 连接触发不受静默期限制 | `checkJoinTrigger()` 提到 60 s 静默期之前 —— 用户明确点了连接就不该被防自旋措施拦住 |

产物：`build/AirportItlwm-Sequoia-M1d4.kext`（md5 `d523410cb546a9b9bf1d983dee110cdd`）。

## 四之八、第四次真机验证（M1d4）：系统压根没下发连接请求

M1d4（`d523410c…`，已确认部署并重启）结果：`wcl-join-attempts` 依旧不存在。

排查发现我们**只发了 WCL 三条生命周期事件中的一条**：

| 事件 | iwn/iwm/iwx | Ath10kHal（修正前） | 作用 |
| --- | --- | --- | --- |
| `IEEE80211_EVT_DRIVER_RESET_BEGIN` | init 开头 | ❌ 没发 | WCL 向系统 post `ResetInterface(0)` = resetInterfacesBegin |
| `IEEE80211_EVT_DRIVER_READY` | init 结尾 | ✅ 发（但只一次） | post `ResetInterface(1)` = resetInterfacesComplete |
| `IEEE80211_EVT_DRIVER_STOPPED` | stop | ❌ 没发 | 扫描/连接收尾、清 join 状态 |

缺失 `RESET_BEGIN` 很可能让系统不认为接口完成过一次完整复位，于是
**菜单能列出网络（来自我们 publish 的 ScanResult），但点选后不下发任何连接请求**
——正好对应真机上"点了毫无反应、`wcl-join-attempts` 为 0、连 legacy
`setASSOCIATE` 也没被调用"。

### M1d5 修正

| 改动 | 说明 |
| --- | --- |
| 补 `DRIVER_RESET_BEGIN` | bring-up 线程一开始就发，与 iwn/iwm 一致 |
| 补 `DRIVER_STOPPED` | `disable()`（非 MAC 重配置路径）与 `detach()` 各发一次 |
| `ath10k-build` 标记 | 发布构建串（本次 `M1d5`），真机判读前先确认跑的是哪一版 |
| 系统请求计数 | `wcl-scan-reqs` / `wcl-assoc-reqs` / `wcl-leave-reqs`：直接区分"系统没叫我们"与"我们拒绝了" |

产物：`build/AirportItlwm-Sequoia-M1d5.kext`（md5 `903914b1b9a157136d8b01516412610b`）。

### 唯一可能与本项目相关的因果链

M1d6 相比 M1d5 唯一触及**关机路径**的改动，是在 `disable()` 里新增：

```cpp
if (!ic.ic_wcl_mac_reconfig && ic.ic_event_handler && driverReadySent)
    ic.ic_event_handler(&ic, IEEE80211_EVT_DRIVER_STOPPED, NULL);   // 关机时也会执行
```

`disable()` 在系统关机时会经 `setPOWER` 被调用；该事件进 WCL 后走
`finishWCLScan/finishWCLJoin` 并向用户态 `postMessage`。若在关机竞态里阻塞，
关机就不干净，NVMe 未收到正常掉电通知 → 下次开机出现 `AppleNvme` assert。

这能解释"之前七八次重启都正常、偏偏这次卡"——**M1d6 是第一个在关机路径上
多发了事件的版本**。

### M1d7 处置

| 改动 | 说明 |
| --- | --- |
| `disable()` 不再发 `DRIVER_STOPPED` | 关机路径恢复成 M1d5 的行为；停机通知只在 `detach()` 发 |
| 其余（`DRIVER_RESET_BEGIN`、build 标记、各入口计数）保留 | 这些只在开机后运行，不碰关机 |

产物：`build/AirportItlwm-Sequoia-M1d7.kext`。

> 教训（写进交接）：**任何在 `disable()`/`detach()` 路径上新增的事件或等待，
> 都会同时出现在系统关机流程里**，必须单独评估其对关机干净程度的影响。

## 五、风险与安全阀

| 风险 | 处置 |
| --- | --- |
| 半成品连接路径影响已然稳定的扫描/菜单 | 全部 d-2 代码用 boot-arg `ath10k_join=1` 开关，默认**关闭**，默认行为与 M1-c3 r4 完全一致 |

| 关联成功后数据面不通 | 先用"能否进 `IEEE80211_S_RUN` + 收到 EAPOL"作为里程碑判据，数据面（DHCP）单独算 |
