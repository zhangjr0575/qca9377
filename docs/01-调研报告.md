# QCA9377 原生 WiFi（AirPort）可行性调研报告

> 目标：在本机 QCA9377 板卡（subsystem `144d:4133`，三星 NP800G5M-X06CN）上，像 itlwm 的 `AirportItlwm` 驱动 Intel 网卡那样，用 Apple 原生 WiFi 栈（IO80211Controller / Skywalk）驱动这块板卡，而不是 Ath10kMac 目前的“以太网 + 配套 App”方式。

## 1. 结论先行

- **技术上可行，但工程量巨大，属“从零移植 ath10k 到 net80211”级别的工作，不是短期的适配。**
- 存在两条可落地的技术路线，推荐 **路线 A（把 Ath10kMac 的硬件层移植成 net80211 驱动，复用 AirportItlwm 的控制器层）**。
- 最乐观也要分多个里程碑推进，第一个可验收里程碑（固件启动 + 原生扫描出网络）即可验证方向是否正确。
- 本机板卡已由 Ath10kMac 验证可用（扫描/连接 WPA2/收发流量），因此**硬件与固件 bring-up 不是风险点**；真正的风险与工作量在“把 ath10k 固件语义映射到 net80211 驱动回调”这一层。

---

## 2. 背景与目标

| 项目 | 说明 |
| --- | --- |
| 本机网卡 | QCA9377，PCI `168c:0042`，subsystem `144d:4133` |
| 已确认驱动 | Ath10kMac（以太网式接口 + `Ath10k Connectivity` App） |
| 目标 | 原生 WiFi：菜单栏 Wi-Fi、系统设置、原生扫描/连接、Apple RSN 握手 |
| 参照实现 | itlwm 的 `AirportItlwm`（Intel 网卡原生 WiFi） |

“原生 WiFi”与当前 Ath10kMac 的区别：

| 能力 | Ath10kMac（当前） | 原生 WiFi（目标） |
| --- | --- | --- |
| 接口类型 | `IOEthernetController` | `IO80211Controller` + Skywalk |
| 扫描/连接入口 | 配套 App | 系统 Wi-Fi 菜单 / 设置 |
| WPA2 四次握手 | 驱动内置 Supplicant | Apple RSN Supplicant |
| AirDrop/AWDL | 不支持 | 需 stub（itlwm 同样不支持 AirDrop） |
| 定位/iCloud/Handoff 等依赖 AirPort 接口的能力 | 不可用 | 可用（受 AWDL 限制） |

## 3. 架构分析

### 3.1 Ath10kMac（QCA9377 现有驱动）

```
Ath10kPCIDevice : IOEthernetController
 ├─ PCI / DMA / CE ring / MSI 中断       (Ath10kPCIDevice.cpp, 7636 行)
 ├─ 固件 bring-up：BMI → HTC → WMI → HTT  (Ath10kBMI/HTC/WMI/Boot)
 ├─ 自研 802.11 MAC 状态机               (Ath10kConnection.hpp, 1612 行)
 │    LinkStage: Disabled→Scan→Start→Peer→Auth→Assoc→Connected
 ├─ 自研 Supplicant（驱动内完成 WPA2 四次握手）(src/shared/Ath10kSupplicant.hpp)
 ├─ 密钥安装：WMI_VDEV_INSTALL_KEY (0x5009)、WMI_PEER_SET_PARAM (0x6004)
 ├─ 数据面：HTT TX/RX                   (Ath10kNetwork.cpp, 1278 行)
 └─ 用户态控制：IOUserClient + Ath10k Connectivity.app
```

要点：
- **硬件层是完整且已验证的**：PCI/DMA/CE/固件下载/WMI/HTT 全部就绪，且针对本机板卡（`144d:4133`）有精确的 board-data payload。
- **MAC 层与安全层是驱动自研的**，与 net80211 无关（全仓库无 `ieee80211` 符号）。
- 密钥安装、peer 管理、Auth/Assoc 帧构建、HT/VHT 协商都已用 WMI 实现，**这些正是移植到 net80211 时需要复用的原语**。

### 3.2 itlwm / AirportItlwm（Intel 原生 WiFi 参照）

```
AirportItlwm : IO80211Controller                 (Apple 私有 802.11 API)
 ├─ Apple80211 ioctl 处理（scan/associate/RSSI/...）(AirportSTAIOCTL.cpp 1531 行)
 ├─ 虚拟接口 / AWDL stub                        (AirportVirtualIOCTL.cpp 534 行)
 ├─ Skywalk 接口层                              (AirportItlwmSkywalkInterface.cpp 1078 行)
 ├─ useAppleRSNSupplicant() = true → Apple 做四次握手
 └─ fHalService → ItlHalService.get80211Controller() → struct ieee80211com
                                                      │
      net80211（OpenBSD 802.11 MAC 状态机，约 21K 行，全部复用）
                                                      │
      ItlIwm/ItlIwx/ItlIwn : ItlHalService          (Intel iwlwifi → net80211 移植)
```

三层结构的关键点：
1. **IO80211Controller 层**：实现 Apple80211 私有 ioctl，这是“原生 WiFi 菜单/设置”的入口。AirportItlwm 已解决 Sequoia（24.x）与 Tahoe（26.x）的 ABI 差异（`AirportItlwm-Sequoia` / `AirportItlwm-Tahoe` 两个 target、`macOS15`/`macOS26` 两套头文件）。
2. **net80211 层**：OpenBSD 的 802.11 协议栈（扫描、认证、关联、密钥管理、AMPDU、节点表）。驱动通过 `ic_*` 回调接入：`ic_newstate`、`ic_set_key`、`ic_delete_key`、`ic_ampdu_tx/rx_start/stop`、`ic_recv_mgmt`、`ic_send_mgmt` 等（见 `itl80211/openbsd/net80211/ieee80211_var.h`）。
3. **HAL 层**：`ItlHalService` 抽象（`attach/detach/enable/disable/get80211Controller/getDriverInfo/getDriverController`），Intel 驱动通过移植 iwlwifi 到 net80211 回调来实现。

### 3.3 关键差距

要实现 QCA9377 原生 WiFi，需要补上中间的 **ath10k → net80211 驱动层**：

```
AirportAth10k : IO80211Controller      ← 直接复用 AirportItlwm 的控制器层
    → ieee80211com (net80211)          ← 直接复用，零改动
        → Ath10kHal : ItlHalService    ← 新增：把 Ath10kMac 的硬件/MAC 映射为 ic_* 回调
```

**没有现成 ath10k 的 net80211 驱动可借用**：
- OpenBSD 对 QCA9377（`0x0042`）报 `not configured`，OpenBSD 只有 `athn`（AR9000 时代老芯片），没有 ath10k。
- Linux 的 `ath10k` 基于 mac80211，与 net80211 框架不同，不能直接搬运，但可作为 WMI/固件语义的权威参考（Ath10kMac 已经参考了 Linux ath10k，注释中大量标注）。

## 4. 逐项技术可行性

### 4.1 固件 bring-up 与硬件驱动 ✅ 已具备
Ath10kMac 已完整实现并通过本机验证。移植时几乎可直接复用其 PCI/CE/DMA/BMI/HTC/WMI/HTT 代码。

### 4.2 net80211 驱动回调映射（核心工作）⚠️ 最大工作量
需将 Ath10kMac 现有能力映射为 net80211 回调：

| net80211 回调 | Ath10kMac 对应能力 | 难度 |
| --- | --- | --- |
| `ic_newstate`（SCAN/AUTH/ASSOC/RUN 状态机） | `LinkStage` 状态机 + WMI mgmt 帧 | 高 |
| 扫描 start/end | WMI scan 命令 + scan 事件解析 | 中 |
| `ic_set_key` / `ic_delete_key` | `buildSecurityWMI`（WMI 0x5009/0x5009 关闭） | 中 |
| `ic_ampdu_tx/rx_start/stop` | HTT 聚合协商 | 中高 |
| 管理帧 tx/rx | Auth/Assoc 帧构建 + WMI mgmt 事件 | 中高 |
| 数据 tx/rx | `submitDataPacket` / `deliverNetworkRX` | 中 |
| `ic_newassoc`、节点管理、RSSI | peer 创建 + 现有 RSSI 解析 | 低中 |

### 4.3 Apple RSN Supplicant 集成 ✅ 原理可行
- 原生路径下 `useAppleRSNSupplicant() = true`，Apple 完成四次握手，驱动通过 `setPTK`/`setGTK` → `ic_set_key` 把密钥下发到固件。
- ath10k 固件本就支持“外部安装 PTK/GTK”（Linux ath10k + wpa_supplicant 即此模式），Ath10kMac 的 `buildSecurityWMI` 已实现该 WMI 命令。
- 因此**可废弃 Ath10kMac 内置 Supplicant**，改用 Apple 下发的密钥走同一 WMI 安装路径，这部分是“减负”而非新增难点。

### 4.4 Apple80211 私有 API / Skywalk ✅ 已被 itlwm 解决
- 复用 AirportItlwm 的控制器层即可规避私有 API 与 Sequoia/Tahoe ABI 差异风险。
- 需为每个目标 macOS 版本各建一个 target（与 AirportItlwm 相同）。

### 4.5 固件与板卡数据 ✅ 已具备
- Ath10kMac 已内嵌本机板卡的精确 board-data（`Ath10kPayload9377Samsung`，`144d:4133`）。
- 只需把 payload 集成进新 kext（勿手改 `Ath10kPayload.hpp`，沿用 `scripts/prepare-firmware.py`）。

### 4.6 暂不支持项（与 AirportItlwm 对齐）
- AWDL/AirDrop、WPA3/SAE、强制 PMF、DFS、AP 模式：首版全部 stub 或显式不支持，与 AirportItlwm 现状一致，不构成阻断。

## 5. 风险与难点

1. **net80211 移植是主要风险与工作量**：iwlwifi→net80211 由 OpenBSD 维护者多年完成；ath10k 无先例，需从 Ath10kMac/Linux ath10k 语义中重写驱动回调，易在扫描事件、assoc 状态机、密钥生命周期、AMPDU 等处出细节错误。
2. **固件“重”型架构的语义差异**：ath10k 固件自行完成扫描/密钥安装/peer 管理，与 net80211 期望的“驱动主导”模型存在阻抗失配；iwlwifi 同属重固件，证明可行，但需精细适配。
3. **Apple RSN 握手与 WMI 密钥时机的衔接**：需验证 Apple Supplicant 下发 PTK/GTK 的时序能被 WMI 正确承接（peer 必须先创建、密码套件需匹配）。
4. **私有 API 脆弱性**：每个 macOS 大版本 ABI 都可能变（itlwm 已用 Sequoia/Tahoe 双 target 应对）。
5. **联调只能在真机/黑苹果上验证**：内核驱动无法在普通模拟环境完整联调，迭代慢。

## 6. 路线对比

| | 路线 A（net80211 移植，推荐） | 路线 B（直接 IO80211Controller 对接 Ath10kMac MAC） | 路线 C（维持以太网，不追求原生） |
| --- | --- | --- | --- |
| 思路 | 新增 `Ath10kHal` 驱动 net80211 | 新写控制器，ioctl 直接调用 Ath10kMac 现有 MAC/Supplicant | 现状 |
| 复用 AirportItlwm 控制器层 | 100% | 部分（ioctl 体与 net80211 深度耦合，需大量改写） | 无 |
| 复用 net80211 | 100% | 无 | 无 |
| 复用 Ath10kMac | 硬件原语 100%；MAC/Supplicant 需重写为回调 | 硬件+MAC+Supplicant 100% | 100% |
| Apple RSN 集成 | 免费（net80211 已支持） | 需自行实现 | 无 |
| 总工作量 | 大（核心在 net80211 驱动层） | 大且更“定制”、可维护性差 | 零 |
| 结论 | **推荐** | 备选 | 不满足目标 |

## 7. 工作量估算（量级参考）

- Ath10kMac 硬件核心约 **11K 行**（含 PCIDevice/Connection/Network/WMI），另有 RX/CE/HTC/BMI/regulatory 等支撑文件。
- AirportItlwm 控制器层约 **5.6K 行**；net80211 约 **21K 行**；Intel HAL（仅 iwm 一代）约 **17K 行**。
- 新增 `Ath10kHal` 预计 **数千行新代码**，且需配套 Xcode target、Info.plist、payload 集成、回归测试。
- 综合判断：这是**数月级全职投入**的工程，建议以“里程碑+可运行增量”方式推进，每个阶段独立可验收。

## 9. 调研结论摘要

1. **可行**，路线 A（Ath10kMac 硬件 → net80211 → AirportItlwm 控制器层）为推荐实现路径。
2. **硬件/固件无风险**（本机板卡已被 Ath10kMac 验证），**风险与工作量集中在 net80211 驱动层移植**。
3. **Apple RSN 集成反而简化**（去掉内置 Supplicant，走 Apple 下发密钥 + WMI 安装）。
4. 建议以 **4~5 个可验收里程碑** 渐进实现，先做“固件启动 + 原生扫描”以验证路线。
5. 首版对齐 AirportItlwm 的能力边界：不支持 AirDrop/AWDL、WPA3、强制 PMF、DFS。
