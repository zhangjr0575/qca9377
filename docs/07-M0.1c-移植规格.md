# M0.1c 移植规格：从冷复位完成到 HTC READY

> 目标读者：把 Ath10kMac 的「固件下载 + HTC 初始化」路径移植进新 net80211 驱动（itlwm `itlwm/hal_ath10k/`）的工程师。
>
> 参考实现：`Ath10kMac/src/kext/Ath10kPCIDevice.cpp`（7636 行）及相关头文件。
>
> 目标芯片：QCA9377，PCI `168c:0042`，subsystem `144d:4133`，chip revision 1 → `hw1.1`，`firmwareDirectory="QCA9377/hw1.0"`，`targetCpuFrequencyHz=176000000`。
>
> 分析方式：只读代码走查。本文所有行号均指当前工作区文件（`Ath10kMac/src/kext/`）中的行号。

## 2. CE（Copy Engine）配置

### 2.1 三个函数

| 函数 | 行号 | 做什么 | 何时调用 |
| --- | --- | --- | --- |
| `allocateCERings()` | 6728–6818 | 把 `kCEHostConfig[]` 里每个 CE 的非零 src/dst ring 用 `Ath10kCERing::allocate()` 分配为物理连续 + 32 位 DMA 可见缓冲，并清零 + 同步到设备。失败时记录 7 项诊断（ceId/direction/stage/status/bytes/dma/segment/phys/align）后 `releaseCERings()` 全回滚 | `runDeferredProbe` 173，**先于冷复位** |
| `initOneCopyEnginePipe()` / `initCopyEnginePipes()` | 3493–3564 / 3566–3596 | 逐 CE 清 ring、`syncForDevice`、写 `SRC/DST_RING_BASE_LO`、`SIZE`、`CTRL1.dmax`、`WATERMARK`，再整体读回用 `verifyCopyEnginePipe()` 校验；失败调用 `deinitCopyEnginePipes()` | `warmResetTarget` 两遍 + 复位后一遍（6504） |
| `deinitOneCopyEnginePipe()` / `deinitCopyEnginePipes()` | 3598–3637 / 3639–3664 | 先清 `SIZE` 再清 `BASE`（撤掉生产者可见性）、清 `WATERMARK`、清 `CTRL1.dmax`，并读回确认 base/size/dmax/watermark 全 0 | P5 之前失败清理（6599）、热复位失败路径、`quiesceTargetAfterBMI` 6244 |

`verifyCopyEnginePipe()`（3462–3491）的判定条件就是移植时的自检清单：

```
非 poll CE： (HOST_IE & 0x1f) == 0  且  (MISC_IE & 0x7e0) == 0
src ring： allocated 且 SRC_BASE == ring.dmaAddress32
           且 SRC_SIZE == entries
           且 (CTRL1 & 0xffff) == srcSizeMax
           且 (CTRL1 & 0x10000) == 0            // 无源字节交换
           且 SRC_WATERMARK == watermarkValue(0, entries)   // == entries
dst ring： DST_BASE / DST_SIZE 同上，(CTRL1 & 0x20000) == 0，DST_WATERMARK == entries
```

### 2.2 CE 分工（QCA6174/QCA9377 共用同一套表）

Host 侧表 `Ath10k::kCEHostConfig[8]`（`Ath10kCE.hpp` 88–97）：

| CE | srcEntries | srcSizeMax | dstEntries | hostIE | 用途（role 字符串） | BMI/HTC 中的角色 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 16 | 256 | 0 | 使能 | HTC control H2T | **BMI 命令 H2T**（`kBMICENumToTarget=0`）；HTC 控制帧 TX |
| 1 | 0 | 2048 | 512 | 使能 | HTT+HTC T2H | **BMI 响应 T2H**（`kBMICENumToHost=1`）；HTC READY / HTC 控制响应 / HTT RX |
| 2 | 0 | 2048 | 128 | 使能 | WMI T2H | WMI 事件（READY/AVAILABLE/SCAN…） |
| 3 | 32 | 2048 | 0 | 使能 | WMI H2T | WMI 命令 |
| 4 | 8192 | 256 | 0 | **disableInterrupt=true** | HTT H2T | 数据发送 |
| 5 | 0 | 0 | 0 | — | 两个芯片上 host 侧未用 | — |
| 6 | 0 | 0 | 0 | — | target 自主（hif_memcpy），只由 P5 的 target pipe 表配置 | — |
| 7 | 2 | 2048 | 2 | — | diagnostic window，`poll=true` | init_config 读/写、只读诊断 |

要点：
- *BMI 只用 CE0（src，16 项）+ CE1（dst，512 项）*。CE1 的 `srcSizeMax=2048` 很关键：它是 target→host 方向单包上限，HTC READY 缓冲正好取 2048（`kHTCReadyBufferBytes`），且 P16 会断言 `(CTRL1 & 0xffff) == 2048`（6037）。
- **CE1 的 `CTRL1.dmax` 不是 host 写的**：`initOneCopyEnginePipe` 只在 `srcEntries != 0` 时才写 dmax（3507–3529），而 CE1 的 `srcEntries == 0`，所以 CE1 的 dmax 依赖复位/ROM 的默认值（实测就是 2048）。`verifyCopyEnginePipe` 也只对 srcEntries!=0 的 CE 检查 dmax（3474–3482），但 P16 会把它当硬前置（6037）。移植时**不要让 CE1 的 CTRL1 被写成 0**，并在 P16 前先读出来确认 == 2048。
- *CE4 的 8192 项 = 64 KiB ring*，正是 README 里那个"只拿到 4 KiB 段"的受害者，DMA 校验必须生效（§3.2）。
- *CE7 是轮询 CE*：`maskTargetIRQsForWarmReset` 跳过它（3333），`stopRuntimeCEIRQ` 也不碰它。

### 2.3 寄存器偏移与写入值（`Ath10kCE.hpp`）

CE 基址 = `kQca6174RegisterLayout.ce0BaseAddress + 0x400 * ceId` = `0x34400 + 0x400*id`（`ceBaseAddress()` 119–122）→ CE0 `0x34400`、CE1 `0x34800`、CE2 `0x34c00`、CE3 `0x35000`、CE4 `0x35400`、CE5 `0x35800`、CE6 `0x35c00`、CE7 `0x36000`；wrapper `0x34000`（只读中断汇总，`inspectCopyEngines` 6697）。

| 偏移 | 名称 | 写值 / 判定 |
| --- | --- | --- |
| `+0x00` | SRC_RING_BASE_LO | `srcRing.dmaAddress32()`（32 位 iovm） |
| `+0x04` | SRC_RING_SIZE | `srcEntries`（**项数**，非字节） |
| `+0x08` | DST_RING_BASE_LO | `dstRing.dmaAddress32()` |
| `+0x0c` | DST_RING_SIZE | `dstEntries` |
| `+0x10` | CTRL1 | 只读-改-写，**且仅在 `srcEntries != 0` 时写 dmax**：`ctrl1 = (ctrl1 & ~(0xffff \| 0x10000)) \| srcSizeMax`；dst 侧仅 `ctrl1 &= ~0x20000`（不动 dmax） |
| `+0x18` | COMMAND | 不写（只读诊断） |
| `+0x2c` | HOST_IE | 全程 0（masked）；运行时仅把 bit0 copy-complete 打开（810–812），watermark 0x1e 保持 0 |
| `+0x30` | HOST_IS | W1C 状态，**只读诊断，不写** |
| `+0x34` | MISC_IE | 0 |
| `+0x38` | MISC_IS | W1C 错误状态，**只读**（诊断读不清除） |
| `+0x3c` | SRC_WRITE_INDEX | **doorbell**：提交 H2T 时写 `ceRingNext(srcSlot, entries)` |
| `+0x40` | DST_WRITE_INDEX | **doorbell**：挂 RX 缓冲时写 `ceRingNext(dstSlot, entries)` |
| `+0x44` | CURRENT_SRC_READ | 只读，H2T 完成判定：`(read & (entries-1)) == next` |
| `+0x48` | CURRENT_DST_READ | 只读，遥测（不作为完成唯一依据） |
| `+0x4c` | SRC_WATERMARK | `watermarkValue(0, srcEntries)` = `srcEntries` |
| `+0x50` | DST_WATERMARK | `watermarkValue(0, dstEntries)` = `dstEntries` |

位域（`Ath10kCE.hpp` 57–75）：`CTRL1.DMAX=[15:0]`、`SRC_BYTE_SWAP=0x10000`、`DST_BYTE_SWAP=0x20000`、`SOFTWARE=0x0007ffff`；`HOST_IE` 中断掩码 `0x1f`（bit0 copy-complete、bit1..4 watermark）；`MISC_IE` 错误掩码 `0x7e0`。

描述符（`Ath10kCE.hpp` 26–32）：qca6174/qca9377 用**旧式 8 字节**格式，`struct CEDescriptor32 { UInt32 address; UInt16 nbytes; UInt16 flags; }`，`static_assert(sizeof == 8)`。

- `address`：本端缓冲的 **32 位 DMA 地址**；诊断写时 dst 描述符里填的是 *target CE 地址*（见 §4.3）。
- `nbytes`：本端缓冲字节数（≤2048 用），也是 RX 完成标志（非 0 即完成）。
- `flags`：transfer_id/metadata 字段。**BMI 用 `0xfffc`**（`kQCA6174CEDescriptorMetadataAnonymous`，BMI 无端点概念），**HTC 控制帧用 0**（endpoint 0）。

### 2.4 ring 大小、对齐、DMA 约束

- 大小 = `entries * 8` 字节：CE0 128 B、CE1 4096 B、CE2 1024 B、CE3 256 B、CE4 65536 B、CE7 16+16 B。合计约 69 KiB。
- entries 必须是 2 的幂（`Ath10kCERing::allocate` 20–24 用 `isPowerOfTwo` 校验），因为 doorbell 索引用 `& (entries-1)` 回绕（`ceRingNext`）。
- 对齐：`kCEDescriptorRingAlign = 8`（`Ath10kCERing` 33 传入；`Ath10kDMABuffer::allocate` 40–41 要求对齐为 2 的幂）。
- **32 位 DMA 地址限制**：`IODMACommand::withSpecification(kIODMACommandOutputHost64, /*numAddressBits=*/32, ...)`（`Ath10kDMA.hpp` 66–74），并在 132–133 显式拒绝 `_dmaAddress > 0xffffffff` 或 `dmaAddress + size - 1 > 0xffffffff`。
- 缓冲区必须物理连续：`IOBufferMemoryDescriptor::inTaskWithPhysicalMask(kIOMemoryPhysicallyContiguous | kIODirectionInOut | kIOMapInhibitCache, size, mask)`（47–52，Role::Ring 走 inhibit cache）。

### 2.5 `Ath10kCERing` 提供了什么

`Ath10kCERing.hpp`（115 行）是 ring 的**纯内存对象**，不碰寄存器：

- `allocate(ceId, direction, entries, IOMapper*)` 15–56：校验 ceId/entries，算字节数，调用内嵌 `Ath10kDMABuffer::allocate(bytes, 8, mapper)`，失败时把 7 项失败的诊断字段原样搬出来（"哪一步失败"可定位到 `contiguous-descriptor-allocation` / `dma-segment-length-invalid` / `dma-address-span-above-32bit` 等）。
- `release()` 58–72；`allocated()`、`entries()`、`bytes()`、`dmaAddress32()`、`virtualAddress()`、`syncForDevice()/syncFromDevice()`、`allocationFailure*()` 等访问器 74–95。
- 它**不负责**：写 CE 寄存器、doorbell、描述符生命周期、完成轮询。这些都在 `Ath10kPCIDevice` 的方法里手写（`initOneCopyEnginePipe`、`bmiExchange` 等）。移植时同样的分层可直接照搬。

### 2.6 target 侧 CE pipe 表与 service map（P5 写入内容，`Ath10kTarget.hpp`）

这两个结构是**写给目标固件/ROM 的**（经 CE7 写到 `pipe_cfg_targ_addr` / `svc_to_pipe_map`），不是 host 寄存器：

`kQCA6174TargetCEConfig[7]`（166–175），每项 `{pipeNum, pipeDir, nEntries, nBytesMax, flags, reserved}` = 24 B，共 168 B：

| pipe | dir | nEntries | nBytesMax |
| --- | --- | --- | --- |
| 0 | Out | 32 | 256 |
| 1 | In | 32 | 2048 |
| 2 | In | 64 | 2048 |
| 3 | Out | 32 | 2048 |
| 4 | Out | 256 | 256 |
| 5 | Out | 32 | 2048 |
| 6 | InOut | 32 | 4096 |

`kQCA6174ServiceMap[17]`（178–197），每项 `{serviceId, pipeDir, pipeNum}` = 12 B，共 204 B；关键映射：`SVC_RSVD_CTRL(0x0001)` out→pipe0 / in→pipe1；`SVC_WMI_CONTROL(0x0100)` out→pipe3 / in→pipe2；`SVC_HTT_DATA(0x0300)` out→pipe4 / in→pipe1；`SVC_TEST_RAW(0xfe00)` out 0 / in 1；最后一项 `{0, kPipeDirNone, 0}`。

## 3. DMA 层

### 3.1 `Ath10kDMABuffer` 契约（`Ath10kDMA.hpp` 262 行）

```cpp
bool allocate(UInt64 size, UInt64 alignment, IOMapper *mapper = nullptr,
              Role role = Role::Ring);
bool syncForDevice();   // CPU 写完 → 交给设备前
bool syncFromDevice();  // 设备写完 → CPU 读前
void release();
UInt64 dmaAddress() const;    // 设备可见（32 位）地址
UInt32 dmaAddress32() const;  // 环形/描述符里填这个
void *virtualAddress() const;
IOPhysicalAddress physicalAddress() const;  // 仅诊断，不要塞进描述符
```

调用契约（**必须遵守**）：

1. `allocate()` 返回 true 后，缓冲区已 `bzero` 并已 `syncForDevice()`（141–144），所以 ring 可以立即编程。
2. 任何"CPU 写 → 设备读"（描述符、请求缓冲、TX 帧）之前必须 `syncForDevice()`。
3. 任何"设备写 → CPU 读"（RX 描述符的 `nbytes`/`address`、响应缓冲内容）之前必须 `syncFromDevice()`，**而且要在每次轮询迭代里都做**——因为 `IODMACommand::kMapped` 在无 IOMMU 时可能使用内部 bounce buffer，CPU 直接读 `virtualAddress()` 看到的是旧数据（3883–3904、4109–4114、4879–4882 均如此）。
4. 描述符里只填 `dmaAddress32()`；`physicalAddress()` 只用于日志。二者在很多机器上不同。
5. `mapper` 传 `IOMapper::copyMapperForDevice(pciNub)` 的结果（387–413）；**返回 nullptr 是合法的**，此时靠默认映射 + 显式同步，绝不能省同步。
6. `Role::Ring`（默认）= `kIOMapInhibitCache`（非缓存，安全）；`Role::Payload` = copyback cache，只用于 HTT 数据面高速路径（`Ath10kNetwork.cpp` 87/564/1151）。**M0.1c 全部用默认 Role::Ring**。

### 3.2 Ath10kMac 踩过的坑：只用首个 IODMACommand 段会静默错位（README 第 30 行）

实现位置：`Ath10kDMA.hpp` 90–136（`allocate()` 内的段遍历循环）。逻辑逐条：

```cpp
UInt64 offset = 0, previousDMAAddress = 0, previousSegmentLength = 0, coveredBytes = 0;
bool firstSegment = true;
while (coveredBytes < size) {
    IODMACommand::Segment64 segment{};
    const UInt64 previousOffset = offset;
    UInt32 numSegments = 1;
    _command->gen64IOVMSegments(&offset, &segment, &numSegments);
    if (numSegments != 1)                      → fail("dma-segment-count-invalid")   // 一次只接受 1 段
    if (segment.fLength == 0 || > size-coveredBytes) → fail("dma-segment-length-invalid")
    if (offset <= previousOffset || offset > size ||
        offset - previousOffset != segment.fLength)  → fail("dma-segment-offset-invalid")
    if (firstSegment) { _dmaAddress = segment.fIOVMAddr; firstSegment = false; }
    else if (segment.fIOVMAddr != previousDMAAddress + previousSegmentLength)
                                               → fail("dma-segments-not-contiguous") // 设备地址必须连续
    previousDMAAddress = segment.fIOVMAddr;
    previousSegmentLength = segment.fLength;
    coveredBytes += segment.fLength;
    _segmentLength = coveredBytes;
}
if (coveredBytes != size) → fail("dma-segment-coverage-incomplete")
if (!_virtual)            → fail("dma-null-virtual-address")
if (_dmaAddress == 0)     → fail("dma-zero-address")
if (_dmaAddress > 0xffffffff || size-1 > 0xffffffff - _dmaAddress)
                          → fail("dma-address-span-above-32bit")
if ((_dmaAddress & (alignment-1)) != 0) → fail("dma-address-misaligned")
```

失败时 `fail()` lambda（25–38）先把 `_dmaAddress/_segmentLength/_physical` 快照下来，再 `release()`，最后填 `_allocationFailure*`——所以日志里能看到"请求 64 KiB、段长只有 4 KiB、DMA 地址是多少"（`allocateCERings` 6762–6770 透传到属性）。

为什么必须这样：旧实现只取第一条段就把 `fIOVMAddr` 当整块基址写进 `SRC_RING_BASE_LO`。若 IOMMU/映射只覆盖了 4 KiB，CE4 的 64 KiB ring 后 60 KiB 的"设备地址"是编造的，设备 DMA 会写到别处 → 设备侧数据损坏、host 侧 DMA 完成后读到垃圾甚至 panic。失败样例：系统睡眠恢复后同一块内存被切成多段。

移植时的等价要求：**要么整段连续（用上面的校验），要么把 ring 缩小到单段（不可取，CE4 固定 8192 项），要么给每个 CE ring 单独重试分配**。最简做法：`allocate()` 失败就重试 3 次；仍失败则 M0.1c 直接失败退出（不要带着错误 ring 继续）。

### 4.2 传输实现

**`bmiExchange()` 4651–5005（有响应）** 时序（与 Linux `ath10k_pci_hif_exchange_bmi_msg` 等价）：

1. 前置校验（4667–4675）：请求/响应尺寸、`_cePipesProgrammed`、`_wakeTargetCPUSucceeded`、CE0 src / CE1 dst 已分配、未处于 uncertain/quarantine/bmiClosed/rxOwned。
2. 懒分配 `_bmiRequestBuffer`(256)/`_bmiResponseBuffer`(256)。
3. 读 CE0/CE1 快照，做**结构性校验** `validateBMIPipeStructure()`（4618–4649，只查 base/size/dmax/byteswap，不查 IE/watermark，因为 `wake_target_cpu` 之后 Linux 也不复查）+ 空闲校验（`srcWriteIndex == currentSrcRead`、`dstWriteIndex == currentDstRead`）。
4. 填请求缓冲 → `syncForDevice`。
5. **先挂 RX**：`rxDesc->address = respBuf.dmaAddress32(); nbytes=0; flags=0` → `CE1_DST_RING.syncForDevice` → 写 `CE1+0x40 = rxNext` → 读回校验。此处起置 `_bmiTransferUncertain = true`（4785）。
6. **再提交 TX**：`txDesc->address = reqBuf.dmaAddress32(); nbytes = requestLength; flags = 0xfffc` → `CE0_SRC_RING.syncForDevice` → 写 `CE0+0x3c = txNext` → 读回校验（4853–4863）。
7. 轮询循环（4872–4908）：每轮 `read32(CE0+0x44)` 与 `read32(CE1+0x48)`；`CE1_DST_RING.syncFromDevice()`；`txDone = (srcRead & (entries-1)) == txNext`；`rxDone = rxDesc->nbytes != 0`。**`rxDone` 只看描述符 nbytes，不等 `CURRENT_DST_READ` 前进**（源码注释 4887–4892 明确说明这是为避免假阴性）。
8. 超时（≥3000 ms）→ `_bmiTimedOut`、记录 wake/RTC 证据、返回 false，并**保持 uncertain**（不重试、不清 W1C）。
9. 成功后：`_bmiTransferUncertain = false`；校验 `completedBytes <= responseLength` → `respBuf.syncFromDevice()` → 拷贝 → 清两个描述符 `nbytes=0` → 两个 ring 再 `syncForDevice()`。

**`bmiSendOnly()` 5301–5391（无响应：WRITE_MEMORY / LZ_* / DONE）**：

- 同样结构校验 + 空闲校验，填 `_bmiRequestBuffer`，只写 CE0 src 描述符（`flags=0xfffc`），提交 `CE0+0x3c`。
- 完成判定：`CE0+0x44` 追上提交值，`IOSleep(1)` 轮询，3 s 超时。
- 只有 `BMI_DONE` 会做额外状态机（5316–5321、5348–5353）：发送前置 `_boot.bmiClosed = true`、`doneAttempted = true`，成功后置 `doneSent`。**DONE 之后任何 BMI 命令都被 `_boot.bmiClosed` 永久拒绝**。
- 关键注释（5388–5390）：CE 消费只证明传输完成，**不证明 ROM 采纳了写入**，所以每个关键写都要靠 BMI_READ_MEMORY 回读（`writeBootHIWord` 5946 就是这么做的）。

> 本仓库没有独立的 `bmiSend`/`bmiRecv` 函数；`bmiExchange` 同时承担两者，`bmiSendOnly` 是只发版。移植时按这两个名字找。

### 4.3 QCA9377 hw1.1 的「diag CE 下载路径」真相

**结论：Ath10kMac 没有实现 Linux 的 `fw_diag_ce_download` 下载路径。**

证据：`firmwareDiagCeDownload` 在整仓库只出现 4 次，全部在 `Ath10kHw.hpp:28`（结构体字段）、`Ath10kHw.hpp:40`（hw1.1 置 true）、以及 3 条日志（`Ath10kPCIDevice.cpp` 2802、3319、5575）。**没有任何分支读取它做下载决策。**

因此 QCA9377 hw1.1 在 Ath10kMac 里的实际路径是：

| 数据 | 通道 | 函数 |
| --- | --- | --- |
| board data (8124 B) | BMI_WRITE_MEMORY，CE0 | `bmiWriteMemory` 5393 → `bmiSendOnly` |
| board 回读校验 | BMI_READ_MEMORY，CE0/CE1 | `bmiReadMemory` 5246 |
| OTP (24193 B) | BMI LZ_STREAM_START(0x1234) → LZ_DATA×98 → LZ_STREAM_START(0) → BMI_EXECUTE | `runBMIOtpTest` 5642 |
| WLAN 固件 (727125 B) | BMI LZ_STREAM_START(0x1234) → LZ_DATA×2932 → LZ_STREAM_START(0) | `runBMIFirmwareDownloadTest` 5811 |
| init_config（CE pipe 表/service map） | **CE7 诊断窗口**（唯一用到 CE7 的功能性写入） | `runCE7InitConfigPersistentTest` 4266 |

CE7 诊断访问与 BMI 的机制差异（这是移植时最容易混的两套 ABI）：

| 维度 | BMI_WRITE_MEMORY | CE7 diag write |
| --- | --- | --- |
| 通道 | CE0 src（H2T） | CE7 src（H2T bounce）+ CE7 dst（目标地址） |
| 命令头 | 有（`id,address,length`，12 B + payload） | **无**，直接裸数据 |
| 地址 | 目标地址放在命令头 | 目标地址要**翻译**成 CE 地址放 `dstDesc->address` |
| 响应 | 无 | 无 |
| 完成判定 | `CE0_CURRENT_SRC_READ == next` | `CE7 CURRENT_SRC_READ == next` **且** `dstDesc->nbytes != 0`，再验 `nbytes == 请求长度` 且 `dstDesc->address == ceAddress`（4141–4145） |
| 单次上限 | 244 B（padded） | 2048 B（`kCEDiagTransferLimit`） |
| 超时 | 3 s | 10 ms（`kCEDiagAccessTimeoutUs=10000`），步进 50 µs（`kCEDiagAccessWaitUs=50`） |
| 失败语义 | `_bmiTransferUncertain` | `_ceDiagTransferUncertain` → `probeTarget` 6552 直接 **禁 bus mastering + 要求重启** |

CE7 目标地址翻译（`targetCpuToCEAddress()` 3666–3681）：

```cpp
coreCtrl = read32(SOC_CORE + 0x00);          // 0x3a000
region      = targetAddress & 0x000fffff;
window      = (coreCtrl & 0x7ff) << 21;      // SOC_CORE_CTRL[10:0] 选择 2 MB 窗口
upperRegion = (targetAddress >= 0x100000) ? 0x00100000 : 0;
ceAddress   = window | upperRegion | region;
```

读方向的描述符正好相反（3775–3781）：`dstDesc->address = bounce.dmaAddress32()`、`srcDesc->address = ceAddress`，**先 post dst（CE7+0x40）再提交 src（CE7+0x3c）**；写方向是 `dstDesc->address = ceAddress`、`srcDesc->address = bounce.dmaAddress32()`（4031–4037），顺序同样是先 dst 后 src。两次都要在 post dst 之后才 `srcRing.syncForDevice()`，并在每次轮询里 `dstRing.syncFromDevice()`。

**【未确认】**：Linux 侧 `fw_diag_ce_download` 到底作用于 board 下载、fw 下载还是两者，本工作区无 Linux 源码可核对（尝试联网拉取被限流）。**移植时不要凭猜测实现 CE7 下载固件**：Ath10kMac 已验证可行的是 BMI 路径。

### 4.4 超时与失败处理（照抄这一套语义就是安全的）

| 机制 | 常量/位置 | 语义 |
| --- | --- | --- |
| BMI 超时 | 3 s，1 ms 步进（`bmiExchange` 4872） | 超时即 `_bmiTransferUncertain = true`，**禁止重试**（DMA 归属不明） |
| BMI 发送超时 | 3 s，1 ms `IOSleep`（`bmiSendOnly` 5362–5379） | 同上 |
| CE7 超时 | 10 ms（diag） | 置 `_ceDiagTransferUncertain` → 禁 bus mastering → 需重启 |
| 固件崩溃指示 | `FW_INDICATOR(0x3a028)` bit0 | 任一阶段读到 bit0 → `_boot.firmwareCrash = true` 并立即失败（6044、6099、1490、1799） |
| 静态门禁 | `_bmiTimedOut / _bmiTransferUncertain / _dmaQuarantine / _boot.bmiClosed / _boot.rxOwned` | 每个 BMI 入口都检查，一旦置位该次上电生命周期内不再继续 |
| 回滚 | `deinitCopyEnginePipes` + `pulseColdResetForQuiesce` 6189 + `quiesceTargetAfterBMI` 6216 | 失败路径：禁 bus mastering → 冷复位 → 重新 wake → deinit CE → 才允许释放 DMA |
| 一次性语义 | `_otpAttempted`、`_fwAttempted`、`_boot.attempted`、`_htcAttempted` | 不允许在同一次上电里重来 |

移植时必须保留的核心不变量：**"提交过 DMA 但完成状态未知" 等同于污染，只能复位，不能重试。**

### 5.3 固件段格式与遍历

`struct FirmwareSegment { UInt32 address; UInt32 offset; UInt32 length; }`（`Ath10kPayloadProfile.hpp` 4）：`address` 是目标 RAM 地址，`offset` 是在 `kFirmware[]` 里的字节偏移，`length` 是该段长度。Samsung 实例（139685–139691）：

```
{0x00980000,     16, 23624}   // fw 主段 A
{0x004144d0,  23648, 10544}   // fw 主段 B
{0x00416e00,  34200, 33704}   // fw 主段 C
{0x00985e00,  67912, 565464}  // fw 主段 D
{0x000a6c00, 633384, 67444}   // fw 主段 E
{0x000a0400, 700836, 26273}   // 入口段（entry 0x000a0400 落在其中）
```

**关键点：段表只用于"下载后回读校验"，不参与下载遍历。**

- 下载：`bmiFirmwareLZData(payload().kFirmware, head)` 把整块 727125 B 镜像（含 72 B SGMT 元数据：magic 8 + 6×8 段头 + entry 标记 8 + DONE 标记 8）作为一个 LZ 流发给 ROM；ROM 自己按 SGMT 解包到各 RAM 段。
- 校验：`verifyFirmwareSegments()` 5764–5809 遍历 6 段，逐段 `bmiReadMemory(segment.address + offset, …)` 比对 `kFirmware[segment.offset + offset]`；读长度按 4 字节上取（`readSize=(count+3)&~3`），**只比较真实字节，不比 padding**（最后一段长度 26273 非 4 对齐，RAM padding 不可预知）。
- 校验前置检查：`length != 0`、`address` 4 字节对齐、`offset/length` 在镜像内、`address + padded(length) ≤ 4 GiB`。

### 5.4 生成脚本 `Ath10kMac/scripts/prepare-firmware.py`（294 行）

是的，`Ath10kPayload.hpp` 由它生成（文件头 `// Generated by scripts/prepare-firmware.py. Do not edit.`）。关键逻辑：

1. 输入 `firmware/QCA9377/hw1.0/{board-2.bin, board.bin, firmware-6.bin}`（1.1 MB，工作区已有）。
2. `select_board()` 47–66：按 `QCA-ATH10K-BOARD\0` 容器遍历 IE，tag0 为普通 board、其内部 subtag0 是名字列表、subtag1 是数据；要求**恰好一条**精确匹配 `bus=pci,vendor=168c,device=0042,subsystem-vendor=144d,subsystem-device=4133`，且长度必须 8124；匹配不到且允许 fallback 时才用 `board.bin`（API1）。
3. `parse_firmware()` 69–89：`QCA-ATH10K\0` 容器，tag0=版本串、tag2=feature bits、tag3=WLAN 镜像、tag4=OTP、tag5/6=WMI/HTT 操作版本（必须 4/3）；**拒绝 tag7（code-swap）**。
4. `ignore_otp_result()` 96–100：feature byte0 bit7 → `kOTPIgnoreResult`；`supports_skip_clock_init()` 102–105：feature byte1 bit1 → `kSupportsSkipClockInit`。
5. `parse_segments()` 108–152：解 SGMT（magic `0x544d4753`），`size==0xffffffff` 为结束、`size==0xfffffffd` 为 entry 地址标记（须 4 对齐且落在某数据段内）、`size & 0x80000000` 拒绝（EXEC/BDDATA）、段地址 4 对齐且 `address+padded(size) ≤ 4 GiB`、段数 ≤64、段不重叠、**不得覆盖 `0x400800..0x404000`（Host Interest + board RAM）**。
6. 9377 两个 profile 有硬编码 SHA256 白名单校验（172–181），board 与固件容器/内容都要对得上，否则构建失败。
7. 输出：`src/kext/Ath10kPayload.hpp`（字节数组 + 段表 + Profile 行 + `selectProfile`）+ `firmware/prepared/QCA9377/{board.bin, otp.bin, firmware-image.bin, manifest.json}`（228–236）。

**移植选项（推荐 B）**：
- A：直接复制 14 MB 的 `Ath10kPayload.hpp`（最简单、零风险，代价是编译时间和 .kext 体积）。
- B：改脚本只生成 Samsung 一个 profile（`prepare()` 250–276 里删掉 6174 与 Dell 两组），体积降到约 4.7 MB / 4.6 万行。
- C：不用编译期数组，运行时读 `firmware/prepared/QCA9377/*.bin`（需要额外的 kext 资源打包机制）；`manifest.json` 已含全部 SHA256 与段表，可作为运行时校验源。

## 6. HTC 阶段

### 6.1 `runHTCServiceSetup()` 1588–1723

前置（1613–1616）：`_runtimeActive && _runtimeCE1Armed && _boot.readyValidated && ready.maxEndpoints!=0 && 0<credits<=255 && _cePipesProgrammed && _htcReadyBuffer.allocated() && !_dmaQuarantine`。

流程：

1. 分配 `_htcControlBuffer`（256 B）。
2. 用 `mapQCA6174ServiceToPipes(kSvcRsvdCtrl)` 得到 reserved-control 的 uplink/downlink pipe（pipe0/pipe1），**endpoint 固定为 0**，`creditFlowEnabled=false`，不向固件发 CONNECT（endpoint 0 是隐式服务）。
3. `HTT_DATA(0x0300)`：`buildHTCConnectServiceFrame(frame, 16, 0x0300, kHTCConnFlagDisableCreditFlow=0x0008)` → `htcSubmitControlFrame(..., expectResponse=true, expectedMessageId=3)` → `parseHTCConnectServiceResponse(..., ready.maxEndpoints, ...)`；成功后 `creditFlowEnabled=false`（非 WMI 服务关流控）。
4. `WMI_CONTROL(0x0100)`：flags = `ready.credits << 8`（READY 里带回的 credit 数放进连接标志高字节），同样走 control 帧交换；成功后 `creditFlowEnabled=true`。
5. 校验两服务 endpoint 不重复（1710–1713）。
6. 本里程碑**不发 SETUP_COMPLETE**：`_htcStatus="services-connected-setup-deferred"`（1716–1718）。SETUP_COMPLETE_EX 在 `runWMIBootstrap()` 1783–1790 发（`buildHTCSetupCompleteExFrame` 20 B，`kHTCMessageSetupCompleteEx=5`），之后在 CE2 上等 WMI SERVICE_AVAILABLE/READY（1792–1850）。

`htcSubmitControlFrame()` 1377–1586：CE0 src 发帧（`flags=0`，byte[5]=endpoint0 序号）、CE1 dst 收响应（复用 `_htcReadyBuffer`），每轮读 `FW_INDICATOR` 查崩溃，超时 2000 ms / 1 ms（`kHTCServiceTimeoutMs/kHTCServicePollMs`）；发完必须 `htcRepostRuntimeReceive()`（1320–1375）把 CE1 下一个槽挂回去。

### 6.2 HTC READY 如何检测

`prepareHTCReadyReceive()` 6026–6079（P16，在发 DONE 之前）：

1. 校验 CE1 `CTRL1.dmax == 2048`、CE1 ring 空闲。
2. 读 `FW_INDICATOR(0x3a028)`，bit0（`kFwIndicatorEventPending`）→ 判定固件崩溃并失败。
3. 分配 `_htcReadyBuffer`（2048 B），`bzero` + `syncForDevice`。
4. 在 CE1 dst ring 当前 `dstWriteIndex` 槽写描述符 `address = buffer.dmaAddress32()`，`nbytes=0`，ring `syncForDevice`。
5. 置 `_boot.rxOwned = true`（此后 CE1 归固件所有，BMI 不得再用它收响应）。
6. 写 doorbell `CE1+0x40 = ceRingNext(slot, 512)`，读回校验 → `_boot.rxPosted = true`。

`waitForHTCReady()` 6081–6156（P18）：

```
循环：
  read32(CE1+0x48) → rxRead（必须在 [slot, next] 之内）
  read32(0x3a028)  → FW_INDICATOR；bit0 → firmware-crash 失败
  ceDstRing.syncFromDevice()
  rxBytes = desc->nbytes;  非 0 即完成（不看 DRRI 是否前进）
  未完成则 IOSleep(1)，累计到 3000 ms（kHTCReadyTimeoutMs）
完成后：desc->address == buffer.dmaAddress32() && rxBytes <= 2048
        htcReadyBuffer.syncFromDevice() → parseHTCReady(bytes, rxBytes, _boot.ready)
```

`parseHTCReady()`（`Ath10kHTC.hpp` 185–244）接受条件（这就是 M0.1c 的验收判据）：

- 帧长 8…2048；`frame[0]==0`（endpoint 0）；`frame[1]` 只允许 bit0(MoreBlock)/bit1(TrailerPresent)。
- `payload = LE16(frame+2)` 不大于实收长度；总长等于 `8+payload` 或 4 字节上取（CE 可能补齐）；不允许第二帧。
- trailer 结构逐条验证（credit 记录 4 B 对齐、lookahead ≥12 B）。
- body = payload − trailer，长度 ∈{8} ∪ [12, 256] 且不在 (8,12) 开区间。
- `LE16(msg) == 1`（HTC_MSG_READY_ID）；`credits!=0`、`creditSize!=0`、`maxEndpoints!=0`。
- 可选扩展（body≥12）：`version(msg[8]) ≤ 1`、`maxBundleMessages(msg[9])`、`altDataCreditSize = LE16(msg+10) & 0x0fff`。

| --- | --- | --- | --- | --- |

## 7. 中断 vs 轮询

### 7.1 Ath10kMac 在 BMI 阶段：**纯轮询，中断全程屏蔽**

| 证据 | 位置 |
| --- | --- |
| 探针跑在 `thread_call`（`THREAD_CALL_PRIORITY_USER`），不在 workloop | `start()` 142–147、`deferredProbeCall` 155–160 |

| `initOneCopyEnginePipe` 从不写 HOST_IE/MISC_IE（靠复位/屏蔽遗留 0），`verifyCopyEnginePipe` 反而断言它们为 0 | 3507–3552 / 3470–3472 |

### 7.2 对新实现的约束

| 约束 | 说明 |
| --- | --- |
| 可以全程同步轮询 | P1–P18 不需要任何中断；MSI/INTx 可完全不做。这是**推荐**的最小实现。 |
| 不要在 workloop / IOCommandGate 里跑 | 全流程 10–20 s，含大量 `IOSleep`。itlwm 的 `itlwm::start()` 在同线程调用 `fHalService->attach(pciNub)`（`itlwm/itlwm.cpp:342`），而 `start()` 在 IOConfigThread 上下文——**在 `Ath10kHal::attach()` 里阻塞是可行的**（iwn/iwx 的 `iwx_load_firmware` 就是同步阻塞的，`ItlIwx.cpp:4890`）。 |
| 若想缩短启动可见性 | 照 Ath10kMac：先 `registerService()` 再 `thread_call_enter()` 跑探测（142–145），接口晚些出现但不拖慢 boot。代价是多线程状态机。 |
| 失败不要 fatal | M0.1c 期间应像 M0.1a/b 一样"失败只置状态属性"，避免 attach 失败导致 kext 摘除、无法取证。 |
| 后续要 HTC/WMI 时 | 才需要 IRQ：CE1 copy-complete + `PCIe INTR_ENABLE` mask + `CORE_CTRL bit11`，且必须按 733–862 的顺序"先清 cause→再 unmask→最后 `enableInterrupt`"。 |

## 8. 移植建议

### 8.1 必需 vs 可暂缓

**必需（缺一不可，按真机验证路径）**

| 项 | 理由 |
| --- | --- |
| CE ring 分配 + 32 位连续段校验 | 没有正确 ring 就没有任何 DMA |
| 热复位（SI0/CPU×2/LF/CE reset）与两遍 CE 管道编程 | ROM 启动契约；复位会清 ring |
| CE7 诊断窗口（读 + 写） | `init_config` 只能通过它写；BMI 的前置条件 |
| `init_config`（pipe_cfg + svc_map + config_flags + hi_early_alloc + hi_option_flag2） | `wakeTargetCPUForBMI` 的硬前置（4589） |
| `wake_target_cpu`（CORE_CTRL |= 0x2000） | ROM 不醒就不回 BMI |
| BMI GET_TARGET_INFO / READ_MEMORY / WRITE_MEMORY / LZ_* / EXECUTE | 全部下载通道 |
| PLL（hw1.1 176 MHz） | `configureTargetPLL()` 失败会阻断后续（6532） |
| Boot Host Interest（5 个字） | 固件启动参数 |
| board + 回读、OTP + EXECUTE、固件 + 回读 | 下载本体与验证 |
| `finishBootHostInterest`（UART off + 终检） | Linux 同序；不改会导致固件串口输出干扰 |
| CE1 挂 1 个 2048 B RX + BMI_DONE ×1 + 等 READY | HTC 起点 |

**可暂缓（M0.1c 不做，不影响"下载成功"判定）**

| 项 | 说明 |
| --- | --- |
| MSI/INTx 注册与运行时中断 | 纯轮询即可 |
| HTC `runHTCServiceSetup`、SETUP_COMPLETE_EX、WMI bootstrap、WMI_INIT | P19 之后 |
| `captureBMIROMEvidence` 全部证据采集（5011–5126 及 `bmiExchange` 内 ~150 行） | 纯诊断，原始 bug 已修 |
| `validateCE0PostResetProgramming` / `programAndVerifyOneCE` / `restoreOneCE` / `verifyOneCEProgrammed` / `verifyOneCERestored`（6351–6383、6828–6980） | **死代码**（无调用点），不要移植 |
| `runDMATest` 6982–7013 | 只验证 DMA 层，可省 |
| `init_config` **回滚**逻辑（4470–4549，约 80 行） | 若接受"失败即冷复位重启"，可只保留"失败→quiesce→报错" |
| 恢复/重连、`_reprobeRequested`、PowerManagement | 与 M0.1c 无关 |
| WMI/HTT/数据面（`Ath10kWMI.hpp`、`Ath10kNetwork.cpp` 等） | 后续里程碑 |

### 8.2 建议的可独立验证子步骤（每步都有寄存器级验收）

> 每步都失败即停、不重试；失败后走 `quiesceTargetAfterBMI` 等价流程（禁 bus mastering → 冷复位）再退出。建议每步把结果 `setProperty`（沿用 M0.1a/b 的 `ath10k-*` 命名）。

| 子步 | 内容 | 验收标准（可直接写进日志/属性） |
| --- | --- | --- |
| **S1** | CE ring 分配（8 个 CE 的全部非零 ring） | 每个 ring：`bytes == entries*8`、`dmaAddress != 0`、`dmaAddress+bytes-1 <= 0xffffffff`、`dmaAddress % 8 == 0`、`gen64IOVMSegments` 全段连续覆盖；CE4 的 64 KiB 必须完整。属性：`ath10k-ce-ring-mask`、失败原因字符串 |
| **S2** | 热复位 + 两遍 CE 管道编程 | `warmResetTarget` 全绿：CE init 成功 2 次、两次 target-init 均看到 `FW_INDICATOR & 2`、`SOC_CHIP_ID` rev 仍为 1；**S2 结束后**每个 CE 的 `SRC/DST_BASE == ring iovm`、`SIZE == entries`、`WRITE_INDEX == 0`、`HOST_IE & 0x1f == 0`、`MISC_IE & 0x7e0 == 0`、`CTRL1.dmax == srcSizeMax`、两个 watermark == entries |
| **S3** | CE7 只读探测 | 4 个值非 0/0xffffffff：`hi_interconnect_state`(0x004008f8) → `pcie_state`；`+0x00` pipe_cfg；`+0x04` svc_map；`+0x20` config_flags。且 `pipe_cfg`/`svc_map` 落在目标 RAM 区（`0x4xxxxx`/`0x5xxxxx` 量级），config_flags bit0（EnableL1）= 期望值 |
| **S4** | init_config 持久写 | pipe_cfg 168 B、svc_map 204 B **写后回读逐字节一致**；config_flags 变为 `orig & ~1`；`hi_early_alloc` = `orig \| 0x6d8a0000 \| 9`（magic 0x6d8a + 9 banks）；`hi_option_flag2` bit4（EARLY_CFG_DONE）置位。四个值全部打印 old→new |
| **S5** | wake_target_cpu + BMI_GET_TARGET_INFO | `CORE_CTRL(0x3a000) bit13` 写入成功；BMI 响应 `length==12 && type==8 && version==0x05020001`。**这是最重要的一步**：它同时证明 CE0/CE1 收发、描述符 flags=0xfffc、doorbell、完成轮询全对 |
| **S6** | HI 前置读 + PLL | 8 个 HI 字全部可读（非 0xffffffff）；`hi_board_data` ∈ [0x401000, 0x404000) 且 4 对齐；`hi_interconnect_state == S3 的 pcie_state`；`hi_option_flag2 & 0x10`；PLL：`0xb2c[10:8]` 得到参考时钟索引（0..7）并打印对应频率、`0x1244` 的 bit5(0x20) **清零**判据两次都通过、三字 `0x404028/0x404020/0x404024` 写成功，status=`configured` |
| **S7** | Boot HI 写 | `HI_APP(0x400800)=2`、`HI_OPTION(0x400810)=orig\|0x2208`、`HI_HOST_BE(0x400844)=0`、`HI_FW_SWAP(0x400904)=0`、`HI_PCI_ID(0x4008bc)=0x0042`，每写一个立刻回读相等 |
| **S8** | board data 上传 | 写后整块 BMI_READ_MEMORY 回读，`SHA256 == cb4aa479…b81d`（或 memcmp）；`hi_board_data_initialized(0x400858) == 1`。**到此为非破坏性里程碑**：固件还没跑，可安全重启 |
| **S9** | OTP LZ + EXECUTE | LZ wire-bytes `== round_up(24193,4) == 24196`、命令数 98；`BMI_EXECUTE` 响应 4 B，`result==0` 或（`kOTPIgnoreResult`）非 0 被接受 |
| **S10** | 固件 LZ 下载 + 回读 | LZ wire-bytes `== 727128`、命令数 2932；下载后复读 GET_TARGET_INFO 与 S5 完全一致；6 段逐段回读字节一致，累计 `727053`；`entry 0x000a0400` 落在某段内。**"最小可验证的固件下载"到此为止**（固件在 RAM 里但未执行） |
| **S11** | 收尾 + DONE + HTC READY | `HI_SERIAL(0x400814)=0`；HI 终检通过（`HI_OPTION` 允许固件加 bit1 `0x2`，用 `bootHIOptionMatchesAfterDownload` 判定）；CE1 挂 2048 B 描述符；DONE 被 CE0 消费；≤3000 ms 内 CE1 `nbytes != 0` 且 `parseHTCReady` 通过，打印 credits/creditSize/maxEndpoints/version |

建议里程碑切分：
- **M0.1c-1 = S1–S5**（CE + 热复位 + init_config + CPU 唤醒 + BMI 握手）
- **M0.1c-2 = S6–S10**（PLL + HI + board + OTP + 固件，**可验证的固件下载**）
- **M0.1c-3 = S11**（DONE + HTC READY）
- M0.2 = HTC 服务 + WMI bootstrap

### 8.4 最危险的 3 个坑

1. **CE ring 的 32 位连续 DMA 段**（`Ath10kDMA.hpp` 90–136）
   只取第一条 `gen64IOVMSegments` 段就把 `fIOVMAddr` 当整块基址 → CE4 的 64 KiB ring 只有前 4 KiB 有效，设备 DMA 写到随机内存。必须整段遍历 + 连续性 + 32 位跨度 + 对齐四重校验；失败重试或直接失败退出。**日志必须打印 requested/segment/dma 三个数**，否则线上无法诊断。

2. **DMA 归属与同步纪律**（`IODMACommand::kMapped` 可能内部 bounce）
   漏一次 `syncForDevice` 就是"设备读到旧描述符"（表现为 CE 永不完成）；漏一次 `syncFromDevice` 就是"CPU 读到旧 nbytes"（表现为永远认为没完成，或把垃圾当响应）。此外顺序不能错：**BMI 先挂 RX 描述符再提交 TX**（`bmiExchange` 4774–4801），**CE7 先 post dst 再提交 src**；一旦提交过就置 uncertain，**绝不重试**——重试会二次 DMA 到已被回收的缓冲，直接 panic。

3. **BMI_DONE 之后的不可逆性 / 复位语义**
   DONE 之前 `_boot.bmiClosed=true` 已经写死（5348–5353），DONE 只能发一次；此后 CE1 归固件所有（`rxOwned`），任何失败都只能走"禁 bus mastering → 冷复位 → 重新 wake → deinit CE"（`quiesceTargetAfterBMI` 6216–6275），绝不能"再发一次命令看看"。同时记住：**热复位会清掉 CE ring 编程**，复位后必须重新 `initCopyEnginePipes`（Linux/Ath10kMac 都在复位里做两遍 + 复位后再做一遍）；`init_config` 一旦写了就不回滚（除非整条失败路径），否则会与 ROM 状态不一致。

> 其余值得注意的坑：`SOC_WAKE` 会被复位清掉，热复位后必须重新 `wakeTarget`（6497–6501）；`HI_OPTION` 必须读-改-写，且下载后固件可能追加 bit1 `0x2`（`kBootHIOptionBMICreditLimit`），终检要用"允许追加"的比较；`FW_INDICATOR` 的 bit0 出现要立刻判崩溃，不要继续轮询。
